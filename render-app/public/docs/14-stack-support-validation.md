**Verdict first: of the six stacks, two work, one is dangerously silent, and three do not work — and the two that "work" are the evidence that the current architecture cannot be extended to the other four.** React and Go both produce real content, but a measured probe of `src/extract/go_extractor.py` shows Go silently misses every generic function, every generic type, every interface method, every closure-returning middleware constructor, and reports nested Fiber group paths one level short — so the project's working belief that Go is its strongest stack does not survive contact with the code. Angular is the single worst output in the repo: it is schema-valid with every content list empty, which means a rendered video that looks finished and says nothing true. Python, Spring Boot and Express hit a placeholder branch at `src/extract/reuse_pipeline.py:80-94` with `confidence: 0` and five schema errors — bad, but loud, and therefore safer than Angular. The central conclusion is not "four extractors need writing." It is that **regex plus brace matching cannot express the facts these stacks are made of** — balanced delimiters, lexical scope, cross-file prefix composition — and that the per-file chunking model is itself the wrong unit for Go (the package is the unit), Angular (component + template + styles) and Spring (the DI graph is not the import graph). Four real defects found during this research are already fixed and under regression test; the remaining work is a parser substrate, with Python as the cheap special case because the stdlib `ast` module parses it perfectly with zero dependencies ([Python `ast` docs](https://docs.python.org/3/library/ast.html)).

## The finding that matters most: Angular is valid, confident-shaped and empty

Python, Spring Boot and Express **fail loudly**. They take the `else` branch at `src/extract/reuse_pipeline.py:85-94`, which emits a record carrying `"notes": "Extraction for stack '<stack>' is not yet implemented in Phase 3."` and `"confidence": 0`. That record is missing `language`, `lineRange`, `frameworkOrLibrary`, `lastUpdated` and `pullRequest`, so schema validation reports `0 valid / 1` (`src/validate/schema_check.py:14-18`), the file card carries `risks: ['extraction confidence is low']`, and a test locks the failure in (`tests/test_schema_check.py:81-96`). Someone reading `pilot_report.json` sees the problem.

Angular does something categorically worse. It is detected correctly (`frontend: 'angular'`), chunked, and routed to `build_frontend_chunk_record` — the real React builder — because the dispatch at `src/extract/reuse_pipeline.py:80` tests `chunk.stack in ("react", "angular")`. The TS regexes then match nothing:

| Angular construct | Regex it must satisfy | Why it fails |
|---|---|---|
| `load() { ... }` class method | `FUNCTION_DECL_RE` needs the `function` keyword; `ARROW_CONST_RE` needs `const x = (…) => {` | `ts_extractor.py:32-43` — class methods have neither |
| `@Input() user!: User` | `INTERFACE_RE` needs `export interface` | `ts_extractor.py:28` |
| `this.http.get('/api/alumni')` | `API_CALL_RE` matches only `api.` / `axios.` | `ts_extractor.py:50-57` |
| `(click)="save()"` in the template | `JSX_ON_PROP_RE` matches `on[A-Z]…={` | `ts_extractor.py:47,62` — and the template is a different file the chunker never opened |

Measured just now against a minimal Angular component with a `@Component` decorator, constructor-injected `HttpClient` and a `load()` method: `importantFunctions []`, `eventHandlers []`, `apiCalls []`, `dataModels []`, `inputs []`, and **`validate_record()` returns an empty problem list** — zero schema errors. Narration produces `"This section covers app, built with @angular/core."` plus `"This part of the code has no further steps to narrate beyond what purpose already covered."` — roughly 28 seconds of speech per file. `build_render_bundle` needs only `script.beats` plus `filePath`/`featureName` (`src/render/render_pipeline.py:160-210`) and never reads `language` or `lineRange`, so the mp4 renders over correctly displayed source with no highlights, because there were no cues to generate.

Before the fix described below, this record also claimed `confidence: 0.95 / "high"` and `risks: []`, with the correct framework name on the card. A reviewer would have read "1/1 valid, confidence high" and concluded Angular worked. **That is the difference that matters: a loud failure costs you a rerun; a silent one ships a video whose every sentence is unfalsifiable by the viewer.** The confidence lie is now fixed (0.3 / `"low"`), but the structural fact is unchanged — Angular still passes schema validation with nothing in it, because an empty list is a valid list.

The root cause is architectural, not a missing regex. Angular's composition is **declarative data plus a separate HTML grammar**, not calls in a render path: `@Component` metadata names `selector`, `template`/`templateUrl`, `styles`/`styleUrl` and an `imports` array, with "[p]aths are relative to the component's directory" ([Angular: Components](https://angular.dev/guide/components)). Resolving `<app-user-card>` to `UserCardComponent` requires a project-wide index of every selector, in three namespaces (element, attribute, pipe). Template expressions "refer to component class members by name" and signals are read by invocation ([Angular: Binding](https://angular.dev/guide/templates/binding)), and the current `@if (x) { … } @else { … }` block syntax nests braces *inside HTML*, which defeats both an HTML tag scanner and a brace counter. Even Compodoc — the Angular-specific precedent, which "just parses your code" with "[n]o TypeScript compilation" ([Compodoc: Features](https://compodoc.app/guides/features.html)) — needs real syntax parsing to handle standalone APIs, signal inputs and default-export route files ([Compodoc README](https://github.com/compodoc/compodoc)). Syntax-level parsing is the floor; regex is below it.

## "Go is our best supported stack" does not survive scrutiny

`documentation/13-known-gaps-and-roadmap.md:10-26` states that "Phase 3's `extract_repo()` only has real builders for React/Angular and Go," which the project has read as *Go is done*. I ran the extractor's own compiled patterns against the constructs the Go research flagged. Results, measured, not inferred:

| Construct | `FUNC_RE` / `STRUCT_RE` result | Consequence |
|---|---|---|
| `func (c *Client) Protect() fiber.Handler {` | `receiver='c *Client', name='Protect'` ✅ | **The receiver-capture bug does not apply here** — `go_extractor.py:17-20` captures the receiver explicitly. Correcting the research note. |
| `func Map[T, U any](xs []T, f func(T) U) []U {` | **no match** | Every generic function is invisible; `\w+\s*\(` cannot pass the `[` |
| `type Store[T any] struct {` | **no match** | Every generic type is invisible (`STRUCT_RE` needs `struct` straight after the name) |
| `func AuthRequired(secret string) fiber.Handler { return func(c fiber.Ctx) error {…} }` | matched, but the inner closure is lost | The dominant Fiber middleware idiom is reported as an ordinary function |
| `type UserRepo interface { FindByID(…) (*User, error) }` | **no match, zero methods** | Interface methods have no `func` keyword at all — so the repository/service boundary, the most important architectural fact in a layered Fiber app, reports as having no behavior |
| `api := app.Group("/api")` then `v1 := api.Group("/v1")` then `v1.Get("/users", …)` | path = **`/v1/users`** | Nested group prefixes do not compose: `go_extractor.py:193-195` stores one level per variable, so the path is **wrong, not missing**, and `prefix_assumed` is False so nothing is flagged |
| `app.Get("/x", func(c fiber.Ctx) error {…})` | handler name = literally **`"func"`** | Fiber v3 inline handlers are named `func` in the narration |

Brace matching fails exactly as predicted. `_find_matching_brace_end_line` (`go_extractor.py:84-97`) is a raw character scan with no string, comment or rune awareness. Measured: a function whose body contains a backtick raw string holding `-- }` reports its range ending at line 2 instead of 3; a function containing `if ch == '}' {` reports line 2 instead of 6. The symptom is a **highlight region desynchronized from the voiceover**, which is the failure mode a viewer notices and cannot diagnose.

Three further Go facts the pipeline has no representation for. First, **version**: Fiber v2 handlers are `func(c *fiber.Ctx) error`, v3 handlers are `func(c fiber.Ctx) error` ([Fiber What's New](https://docs.gofiber.io/whats_new)), and `uses_fiber` is derived only from `"gofiber/fiber" in go.mod` (`src/extract/reuse_pipeline.py:58`) — version-blind. Second, **struct tags carry the content**: `json:` tags define the exact wire shape and `gorm:` tags the table mapping, embedded `gorm.Model` silently adds four columns and soft-delete behavior ([GORM models](https://gorm.io/docs/models.html)), and `gorm:"embedded"` flattens a named struct's fields into the parent — so even the field set is not literal in the source. An extractor that reports struct field names and Go types without parsing tags reports the less useful half. Third, **the package is the unit, not the file**: files in a Go package share one scope with no import statement between them, a method can be declared in a different file from its receiver type, and `go/doc.Package` carries `Filenames` plural ([go/doc](https://pkg.go.dev/go/doc)) — the standard library's own unit of documentation is the package. A per-file chunk for `service/user.go` cannot show the type its methods hang off.

One claim in the Go research is **not citable and should not be repeated**: a widely-shared article attributes the "project-layout is not a standard" position to Russ Cox, but issue #278 contains no statement from any Go team member. The only solid version is the repo's own disclaimer that the layout is "NOT an official standard defined by the core Go dev team" ([golang-standards/project-layout](https://github.com/golang-standards/project-layout)). Do not attribute the quote.

## The real conclusion: a structural ceiling, and a chunking model that is wrong three times over

### Regex cannot express the facts, by construction

Matching balanced `{`…`}` across arbitrary nesting is not expressible as a regular expression — it needs a stack. Python's `re` has no recursion. So **every "where does this thing end" answer in the pipeline is approximate by construction**, which is why `tree-sitter-typescript` ships *two separate grammars* "because TypeScript and TSX are different dialects" ([PyPI: tree-sitter-typescript](https://pypi.org/project/tree-sitter-typescript/)): `<` is generic-open, less-than, or JSX-open depending on tokenizer state, and no pattern can decide that. The TypeScript compiler API's answer to "what is this construct's extent" is to ask the parser — a `SourceFile` "holds both the text and the AST" and traversal is structural via `ts.forEachChild` ([TypeScript wiki](https://github.com/microsoft/TypeScript/wiki/Using-the-Compiler-API)). Regex also has no notion of lexical scope, which is why Fiber's `app.Route(prefix, func(r fiber.Router){…})` and Chi's identically-shaped `r.Route` — both of which **rebind the same identifier to a new sub-router inside the closure** — are bugs the current extractor cannot even represent.

Severity ordering for a narration product, which should drive the fix order: **silent wrong attribution** (a hook, a dependency or a route assigned to the wrong declaration) is worse than **truncated ranges** (highlight desync), which is worse than **missed items** (incomplete but honest).

### The cross-cutting killer: a route's full path lives in another file

This is the single defect shared by Express, Go Fiber and Spring, and it produces a *wrong* answer rather than a missing one — a narrated URL that does not exist in the running app.

| Stack | Where the prefix lives | What a per-method regex reports |
|---|---|---|
| **Spring** | class-level `@RequestMapping("/persons")` concatenated with method-level `@GetMapping("/{id}")` — the docs' own example annotates this as "effectively /persons/{id}", and a bare `@PostMapping` is "effectively /persons" ([Spring: Mapping Requests](https://docs.spring.io/spring-framework/reference/7.0/web/webflux/controller/ann-requestmapping.html)) | `/{id}` |
| **Express** | `app.use('/birds', birds)` in the parent file; the route file says `'/about'` and the real URL is `/birds/about`, transitively through further mounts ([Express routing](https://expressjs.com/en/guide/routing.html)) | `/about` |
| **Go Fiber** | nested `Group` calls — "[r]outes are flattened with their group prefixes," `app.Group("/api")` → `.Group("/v1")` → `.Get("/list")` = `/api/v1/list` ([Fiber grouping](https://docs.gofiber.io/guide/grouping)) | `/v1/list` (measured) |
| **Python FastAPI** | `APIRouter(prefix="/items")` plus `app.include_router(…, prefix="/admin")`, and the router variable "can be named anything" ([FastAPI: Bigger Applications](https://fastapi.tiangolo.com/tutorial/bigger-applications/)) | `/{item_id}` |
| **Python Flask** | `register_blueprint(bp, url_prefix='/pages')`; the decorator only "record[s] the intention of registering" ([Flask Blueprints](https://flask.palletsprojects.com/en/stable/blueprints/)) | `/<page>` |

Express makes it worse still: the full URL requires four linked facts, three of which are outside the route's file — which local identifier holds the Router, what the file exports, which import binds to it in the parent, and which `app.use` prefix applies — and Node's extensionless resolution (`require('./birds')` → `birds.js`, `birds/index.js`, `.mjs`, `.cjs`) must be reimplemented to walk those edges. Nothing in the ecosystem solves this statically: `express-list-endpoints` needs a live app instance, warns that "before call this script the router or app must have the endpoints registered," and is Express 4 only ([express-list-endpoints](https://github.com/AlbertoFdzM/express-list-endpoints)). **Path resolution is a project-wide dataflow pass, not a parsing concern**, and it is the same pass in all five cases.

### Per-file chunking is the wrong unit three times

- **Go**: the package is the unit (above). Package = chapter, file = scene.
- **Angular**: one logical unit is 2–4 files — class, template, styles, spec. Narrating the `.ts` alone yields an explanation with no UI in it; narrating the `.html` alone yields one with no logic. The chunk must be a **component bundle** with `templateUrl`/`styleUrl` resolved relative to the component's directory ([Angular: Components](https://angular.dev/guide/components)) at *chunk-planning* time — which means framework detection must precede chunking, not follow it.
- **Spring**: the DI graph is not the import graph, and getting this wrong is silent and backwards. `OrderController` imports and constructor-injects `OrderService`, an *interface*; nothing in its source mentions `OrderServiceImpl`. An import-based graph therefore presents the application's main business logic class as **having zero inbound edges — dead code**. Injection is by type ([Spring: Using @Autowired](https://docs.spring.io/spring-framework/reference/core/beans/annotation-config/autowired.html)), `@Autowired` is frequently absent because "[i]f a class only declares a single constructor to begin with, it will always be used," and Spring Data repository implementations **do not exist as source files at all** — Spring "create[s] proxy instances for those interfaces" routed to `SimpleJpaRepository` ([Spring Data JPA](https://docs.spring.io/spring-data/jpa/docs/3.1.12/reference/html/)). `@Scheduled`, `@EventListener`, `@ExceptionHandler`, `@Aspect` advice and handler methods all likewise have zero in-project callers and must be labelled "invoked by the container," not "unused." The chunk unit is the **annotated type**, and the narrative unit is the **feature slice** — which is also what Spring's own recommended layout looks like: `customer/{Customer, CustomerController, CustomerService, CustomerRepository}` ([Spring Boot: Structuring Your Code](https://docs.spring.io/spring-boot/3.5.0/reference/using/structuring-your-code.html)).

## What each stack actually needs

### Python — the cheap win, and the only stack with a zero-dependency answer

Brace matching has nothing to match in Python; pointed at a Python file it picks an arbitrary dict literal and reports a function that "ends" mid-body, silently. The stdlib fixes this outright: since 3.8 every positioned node carries `end_lineno`/`end_col_offset`, "the first and last line numbers of source text span," plus `ast.get_source_segment` ([Python `ast` docs](https://docs.python.org/3/library/ast.html); [What's New in 3.8](https://docs.python.org/3/whatsnew/3.8.html)). One `ast.parse()` per file, C-implemented, same interpreter the pipeline already runs under, **zero third-party dependencies**. Three traps to encode: `node.lineno` for a decorated function points at the `def`, not the first decorator, so a full-definition clip must start at `min(d.lineno for d in node.decorator_list)` — otherwise the clip cuts off `@app.get("/items")`, the one line that says what the function is; `end_lineno` is typed `int?` and can be `None`; and `ast.walk` yields nodes "in no specified order," so it must not drive narrative ordering.

The doc-comment reader at `src/extract/function_context.py:45-99` understands only `//` and `/* */` and scans *upward*. A Python docstring is the first statement *inside* the suite, so the correct call is `ast.get_docstring(node, clean=True)`, which also does the dedent. A comment block above a Python `def` is usually a TODO or section marker — reporting it as documentation is actively misleading. Visibility is a computed judgement, not a pattern: PEP 8 says "modules should explicitly declare the names in their public API using the `__all__` attribute," "[d]ocumented interfaces are considered public," "[i]mported names should always be considered an implementation detail," and internality is inherited — "[a]n interface is also considered internal if any containing namespace… is considered internal" ([PEP 8](https://peps.python.org/pep-0008/)). So report tri-state provenance (`declared_in_all` / `public_by_convention` / `private_by_underscore`), never a boolean; note that `is_exported` currently falls back to `signature.startswith("export")` (`function_context.py:159-163`), which marks every Python and Java declaration unexported. Framework-specifically: Django's semantics live in the **filename**, so dispatch on path before parsing, exclude `migrations/` by default (highest line count, lowest explanatory value), and resolve `include("polls.urls")` as a package lookup; FastAPI's `Depends` graph is statically extractable from `Annotated[T, Depends(fn)]` and is the most explanation-worthy diagram in the app; Flask's `app` often does not exist at module scope at all, so anchoring on `app = Flask(` finds nothing in exactly the well-structured codebases worth explaining.

### Express / Node — fix detection first, it is currently unrepresentable

There is no `"express"` or `"node"` value anywhere in `src/detect/project_type.py`; any `package.json` is a *frontend* marker (`:26-31`), and a non-React non-Angular one yields `"react_or_angular"` (`:97-108`), which the chunker propagates into `Feature.stack` and every `ChunkPlan` (`src/chunk/chunker.py:49`; `src/chunk/chunk_splitter.py:79,93`). The measured result on a conventional Express layout is two features both at `confidence 0` with the note `Extraction for stack 'react_or_angular' is not yet implemented in Phase 3.` This is a type-level gap, not a tuning gap.

Then: a `.js` file's module system is not determined by its contents but by the nearest `package.json` `type` field — "`.mjs` is always ES module and `.cjs` is always CommonJS. A `.js` file follows the package's `"type"` field" ([Node packages](https://www.mintlify.com/nodejs/node/api/packages)) — so a project-level metadata read must precede per-file parsing. Express offers at least seven syntactically distinct route registration forms, including chained `app.route('/book').get().post()`, `app.all`, handler arrays, regex-literal paths, and two legitimate declarations of the same path separated by `next('route')` ([Express routing](https://expressjs.com/en/guide/routing.html)). Middleware is classified by **arity**, not name: "Error-handling middleware always takes *four* arguments. You must provide four arguments to identify it as an error-handling middleware function" ([Express middleware](https://expressjs.com/en/guide/using-middleware.html)) — cheap from an AST, impossible from regex across a multi-line arrow with minified parameter names. **The ordered middleware chain is the highest-value Express artifact and the pipeline extracts nothing like it**; order is semantics, recoverable only from statement position, and an error handler registered before routes will never fire. Two more structural requirements: async wrappers (`asyncHandler(async (req,res) => …)`) put the real handler one call-expression deeper, so an extractor that does not unwrap them names the handler `asyncHandler` and highlights the wrong lines; and because plain JS has no types, the request/response shapes must be recovered from Mongoose `new Schema({…})` and `ref`, Sequelize `define`/`hasMany`/`belongsToMany` ([Mongoose populate docs](https://github.com/automattic/mongoose/blob/master/docs/populate.md), [Sequelize model.js](https://github.com/sequelize/sequelize/blob/main/packages/core/src/model.js)) and from Zod/Joi validation schemas bound to the route — all object literals, where the AST-over-regex gain is largest. Finally, Express prescribes no layout: practitioners report "very few of them follow the same organization" ([Project structure for an Express REST API](https://dev.to/ccleary00/project-structure-for-an-express-rest-api-when-there-is-no-standard-way-4gk3)), so **the mount graph is the architecture** and folder names are a labelling hint only.

### Spring Boot — the annotation is the meaning, and the license header is a trap

Role comes from the type-level annotation, not the code shape: `@Component` "is a generic stereotype," with `@Repository`, `@Service` and `@Controller` as "specializations… in the persistence, service, and presentation layers, respectively," and the stereotypes are **meta-annotated**, so `@RestController` does not contain the text `@Controller` ([Spring: Classpath Scanning](https://docs.spring.io/spring-framework/reference/7.1/core/beans/classpath-scanning.html)). A literal string matcher is structurally incomplete and misses project-local composed annotations entirely. Two files of identical Java syntax can be a web endpoint, a transactional service, or inert plumbing.

The repository case breaks the pipeline's core assumption outright: **there is no function body**, so brace matching returns an empty range and an extractor reports "0 functions, no implementation" for the file that defines the entire data-access API. The payload is the method *name*, which **is** the query — "[p]arsing query method names is divided into subject and predicate," concatenated with `And`/`Or`, with `OrderBy`, `Distinct`, `Top`/`First` and `_` for nested traversal ([Spring Data JPA](https://docs.spring.io/spring-data/jpa/docs/3.1.12/reference/html/)).

Visibility: the token `export` never appears in Java, and the Go capital-letter rule is uncorrelated with the truth — every Java class name is capitalized by convention while `public void save()` reads as internal. Worse, absent-modifier means *different things by context*: package-private in a class body, implicitly `public` on an interface member — so a single rule mislabels every repository method in the project. And Lombok (`@Data`, `@Getter`, `@RequiredArgsConstructor`) creates public members that appear nowhere in the source, often removing the constructor that holds the injection points, in which case the `private final` fields *are* the injection points.

Doc comments carry one high-severity trap. A generic `/\*[\s\S]*?\*/` matcher cannot distinguish `/**` from `/*`, and essentially every corporate Java file opens with a license block — **so the class-level explanation for every file becomes a license notice**. Javadoc also legitimately contains embedded HTML (`<p>`, `<pre>`, `&#064;`) which must be stripped before TTS or the narration speaks markup; `@param <E> desc` looks exactly like a JSDoc type brace; asterisk stripping must be per-line and conditional, because "[i]f you omit the leading asterisk on a line, then the leading whitespace is no longer removed" to preserve pasted code examples; and an `@Override` method with no comment may be fully documented on a supertype via the rule that "a missing item is considered as if it were provided with `{@inheritDoc}`" ([Oracle: Doc Comment Spec](https://docs.oracle.com/en/java/javase/22/docs/specs/javadoc/doc-comment-spec.html)). Annotations also sit *between* the doc comment and the declaration, so a "comment on the line immediately above" rule fails on every Spring controller.

The route-path regex has one more nasty literal: `{name:[a-z]+}` is a valid path variable ([Spring: Mapping Requests](https://docs.spring.io/spring-framework/reference/7.0/web/webflux/controller/ann-requestmapping.html)), so a naive `\{(\w+)\}` misses it while `\{([^}]+)\}` yields `name:[a-z]+` as the variable name — split on the first `:`. Paths can also be `${…}` placeholders or SpEL `#{…}`, which must be reported as unresolved rather than verbatim; `@GetMapping` transparently serves HEAD; and `consumes`/`produces` behave *opposite* to path — a method-level value "overrides rather than extends the class-level declaration."

### React — works, with two known wrong-attribution risks

The two most damaging React failures are not missing items. First, **wrong line ranges**, from brace counting across `style={{…}}`, template literals containing `}`, and nested arrow callbacks — which desynchronizes the highlight from the voiceover. Second, **wrong component identity** under `memo`/`forwardRef`/HOC wrapping: `memo` "doesn't modify it; it returns a new memoized component," and the documented idiom nests the definition inside the call ([React: `memo`](https://react.dev/reference/react/memo)), so the exported name, display name and inner function name can all differ and a `const X =` pattern reports `memo` as the component — naming a thing the viewer cannot find on screen. A third, subtler one: hooks are legal only at the top level of a component body or custom hook ([React: Rules of Hooks](https://react.dev/reference/rules/rules-of-hooks)), so a file-wide `use[A-Z]\w*(` scan attributes a nested or second component's hooks to the wrong declaration — wrong state ownership, the most misleading React error available. Correct attribution requires true node ranges, which is precisely what a parser gives and a regex cannot.

## Recommended sequence

| # | Work | Why now | Cost |
|---|---|---|---|
| 1 | **Python extractor on stdlib `ast`** | Exact line ranges, decorators, docstrings, typed signatures, `__all__`, Pydantic/dataclass/SQLAlchemy data models — all from one `ast.parse()`, no new dependency, same interpreter | Lowest cost, highest certainty |
| 2 | **Add `fidelity: regex \| syntax \| typed` to every chunk record** | Lets the narration generator hedge instead of asserting. Pair it with the rule that **refusing to narrate is better output than guessing** — detect the framework and version, and say "routes for this framework are not analyzed" rather than emit an empty or wrong route table | Hours; unblocks honest output everywhere else |
| 3 | **Fix Express detection** — add a real `express`/`node` backend stack value | Currently unrepresentable in `ProjectType`; no extractor work can land until a chunk can carry the right stack label | Small, mechanical |
| 4 | **tree-sitter as the parser substrate** for TS/TSX, JS, Go and Java | One `pip install` per grammar, prebuilt wheels, no Node or Go sidecar, no JVM; byte-accurate spans kill the brace problem outright; error-tolerant, so one odd file does not fail a run; declarative S-expression queries replace each regex. For Java this removes 12 of 14 catalogued breakages in a single change | Moderate; pin grammar versions, node names are not stable across releases |
| 5 | **Reframe chunking per stack** — Go package-level, Angular component bundles (`templateUrl`/`styleUrl` resolved at plan time), Spring per annotated type grouped into feature slices | These are planning-stage changes; doing them after the extractors are written means writing them twice. Note this forces framework detection *before* chunking | Moderate, touches `src/chunk/` |
| 6 | **One shared route-prefix resolver** — a dataflow pass over the tree, emitting `assumed: true` for any non-literal prefix | The same pass serves Fiber groups, Express mounts, Spring class-level mappings, FastAPI routers and Flask blueprints. It is independent of the parser choice, so sequence it after (4) | The single largest correctness win per unit of work |
| 7 | **Optional typed tier, only where it pays** | A Go helper binary using `go/parser` + `go/doc` gets receivers, embedding depth, grouped decls, `IllegalPrefixes` handling and `_test.go` examples for free ([go/doc](https://pkg.go.dev/go/doc)); `go/packages`/`go/types` answers implicit interface satisfaction. A JVM sidecar with JavaParser + `CombinedTypeSolver` resolves the Spring DI graph correctly — "a name like `foo`… only gets its meaning from the declarations that live elsewhere" ([JavaParser symbol resolution](https://tessl.io/registry/tessl/maven-com-github-javaparser--javaparser-core/3.27.0/files/docs/symbol-resolution.md)). Both require the project to *build*, so both must be optional and degrade to `fidelity: syntax` | High; defer until (1)–(6) are in |

Do **not** add a Python-side JS parser as a fallback: `esprima-python`/`pyjsparser` handle ES5/ES6 JavaScript, not TypeScript type syntax, generics, decorators or JSX, so they fail on essentially every file in a modern repo. For Angular specifically, running Compodoc once and consuming its JSON export supplies the route graph and DI graph for free ([Compodoc README](https://github.com/compodoc/compodoc)) — a large fraction of the problem, at the cost of being Angular-only. And one behavioural change independent of all parsing: **schema validation is currently report-only** (`src/pilot/run_pilot.py:35-64` records `schemaValidation.invalid` and then unconditionally narrates and renders every record). A stack with no extractor should not produce an mp4.

## Limits of this research — carry these caveats, do not launder them

Several sources were blocked or rate-limited, and some claims above rest on inference rather than citation. Three specific ones to flag before acting:

- **The Fiber path-parameter syntax list is uncited.** `https://docs.gofiber.io/guide/routing` could not be fetched, so the exhaustive set (`:param`, `:param?`, `+`, `*`, constraints like `:id<int>`) is not sourced here. Verify before the pipeline claims to normalize Fiber route contracts.
- **The `tree-sitter-go` PyPI package name is unconfirmed.** Its PyPI page was blocked. The py-tree-sitter README documents the `tree-sitter-<lang>` wheel convention with `tree-sitter-python` as its example and does not mention Go ([py-tree-sitter](https://github.com/tree-sitter/py-tree-sitter)). Check `pip index` before pinning. The same uncertainty applies to `tree_sitter_java` vs the bundled `tree-sitter-languages`, and to whether `javalang` supports records, text blocks and sealed types — that limitation is inferred from its age, not measured.
- **The "Russ Cox said so" quote about `golang-standards/project-layout` could not be verified and must not be attributed.** Issue #278 contains no Go-team statement. Cite the README's own disclaimer instead.

Further caveats: the Angular DI findings rest on a doc page that now presents only `inject()` — constructor-parameter injection and `@Inject`, still dominant in real codebases, are described from engineering knowledge, so re-verify before hard-coding either form as "the" idiom. Spring's MVC request-mapping page was blocked and the findings come from the WebFlux mirror; the class/method concatenation rule and all annotation names are identical, but the two pages differ on suffix pattern matching. JPA annotation semantics (`@Entity`, `@OneToMany`, `@JoinColumn`), `@Query`/`@Modifying`, and `@Qualifier`/`@Primary` precedence are uncited. `server.servlet.context-path` prepends a further prefix from `application.properties` that would make even a correctly concatenated Spring path incomplete — flagged, unverified. Zod/Joi API surfaces, the complete TypeScript-supported JSDoc tag list, Go 1.22's `net/http` method-in-pattern routing, and specific `asyncHandler` package names are all uncited. Pydantic v1/v2 decorator names are inference. No benchmark exists comparing regex-vs-AST extraction error rates, tree-sitter vs compiler-API accuracy, or Express endpoint extraction across tools — the failure catalogues above are reasoned from language constructs and, where marked "measured," from probes against this repo's own compiled patterns. Finally, **no published source was found on narrative ordering for code-explanation video specifically**; every ordering recommendation is reasoned from each framework's own documented dispatch order, not from evidence about viewer comprehension. The audit's fixtures were minimal synthetic repos: the mechanisms are proven, per-file yield on a large real repo is not, and the Remotion render and TTS were never executed.

## Conclusion

The honest reframing is that this pipeline does not have a coverage problem, it has a **substrate problem**. Two of six stacks produce content, and both of them produce it with known silent inaccuracies that a parser would eliminate for free — Go's wrong nested-group paths and invisible interfaces, React's wrong ranges under JSX braces. Writing four more regex extractors would multiply that error surface by three while adding, for Spring and Express, failure modes that are categorically worse than anything in the repo today: a DI graph that presents the main business logic class as dead code, and a route table full of URLs that do not exist. The cheapest correct move is the smallest one — put Python on `ast`, which costs nothing and is exactly right — and then move the remaining stacks onto tree-sitter before, not after, writing their extraction logic.

The second reframing is about what the product owes its viewer. A code-explanation video is an unusually unfalsifiable artifact: a wrong path, a wrong component name or a highlight that trails the voiceover by eleven lines is undetectable to the person watching, which is the whole reason they are watching. That asymmetry makes **the `fidelity` field and the willingness to refuse** the most valuable features on the list, ahead of any extractor. "Routes for Fiber v3 are not analyzed by this version" is a sentence a viewer can act on. `/v1/users` for an endpoint that is actually `/api/v1/users` is not — and the pipeline currently says it with no `assumed` flag at all.
