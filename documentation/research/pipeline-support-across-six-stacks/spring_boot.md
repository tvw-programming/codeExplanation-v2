# Java Spring Boot: what a static analyzer must understand to explain a file accurately

Scope note: the target pipeline is Python, regex-based (no AST), extracts function/class definitions + line ranges, event handlers, API calls, data models, imports, routes and leading doc comments, decides "exported" by a literal `export` prefix (TS) or a leading capital letter (Go), and finds bodies by brace matching. Every finding below is judged against that baseline.

Blocked sources (do not retry): `docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-requestmapping.html`, `docs.spring.io/spring-framework/reference/core/beans/dependencies/factory-collaborators.html`, `pypi.org/project/javalang/`, `pypi.org/project/tree-sitter-java/` — all returned PROVENANCE_REQUIRED. Equivalent content was obtained from the WebFlux mirror of the request-mapping page, the `@Autowired` page, and other sources; the javalang/tree-sitter-java PyPI metadata could not be verified and is listed as a gap.

## What are the units of meaning in a Spring Boot app that a viewer needs explained?

### Takeaway
The explainable unit in Spring Boot is not "the function" or "the file" but **the annotated type and its role in the container** — entry point, configuration, controller, service, repository, entity, DTO — because the annotation, not the code shape, is what tells you what the class does. Two files with identical Java syntax (`public class Foo { ... }`) can be a web endpoint, a transactional service, or inert plumbing depending on one line above the class declaration.

### Cited Findings
- `@Component` "is a generic stereotype for any Spring-managed component", and `@Repository`, `@Service`, and `@Controller` "are specializations of `@Component` for more specific use cases (in the persistence, service, and presentation layers, respectively)" — [Spring Framework, Classpath Scanning and Managed Components](https://docs.spring.io/spring-framework/reference/7.1/core/beans/classpath-scanning.html)
- The stereotypes are **meta-annotated** with `@Component`: "The `@Component` meta-annotation causes `@Service` to be treated in the same way as `@Component`." Spring also supports "composed annotations" — "the `@RestController` annotation from Spring MVC is composed of `@Controller` and `@ResponseBody`." — [Spring Framework, Classpath Scanning](https://docs.spring.io/spring-framework/reference/7.1/core/beans/classpath-scanning.html)
- `@Repository` "is a marker for any class that fulfills the role or *stereotype* of a repository (also known as Data Access Object or DAO). Among the uses of this marker is the automatic translation of exceptions" — [Spring Framework, Classpath Scanning](https://docs.spring.io/spring-framework/reference/7.1/core/beans/classpath-scanning.html)
- A detected component's **bean name** is generated by `AnnotationBeanNameGenerator`: an explicit `value` wins (`@Service("myMovieLister")` → `myMovieLister`), otherwise "the default bean name generator returns the uncapitalized non-qualified class name" (`MovieFinderImpl` → `movieFinderImpl`) — [Spring Framework, Classpath Scanning](https://docs.spring.io/spring-framework/reference/7.1/core/beans/classpath-scanning.html)
- The entry point: "The `@SpringBootApplication` annotation is often placed on your main class, and it implicitly defines a base 'search package' for certain items. For example, if you are writing a JPA application, the package of the `@SpringBootApplication` annotated class is used to search for `@Entity` items." If you don't want `@SpringBootApplication`, "the `@EnableAutoConfiguration` and `@ComponentScan` annotations that it imports defines that behavior" — [Spring Boot, Structuring Your Code](https://docs.spring.io/spring-boot/3.5.0/reference/using/structuring-your-code.html)
- The canonical entry file is tiny and almost all of its meaning is in the annotation plus one static call: `@SpringBootApplication public class MyApplication { public static void main(String[] args) { SpringApplication.run(MyApplication.class, args); } }` — [Spring Boot, Structuring Your Code](https://docs.spring.io/spring-boot/3.5.0/reference/using/structuring-your-code.html)
- `@Configuration` classes carry `@ComponentScan`, whose `basePackages`/`value` "support `${…}` property placeholders which are resolved against the `Environment` as well as Ant-style package patterns such as `org.example.**`" — [Spring Framework, Classpath Scanning](https://docs.spring.io/spring-framework/reference/7.1/core/beans/classpath-scanning.html)
- Repositories are **interfaces with no bodies**: "Declare an interface extending Repository or one of its subinterfaces and type it to the domain class and ID type that it should handle", then "Set up Spring to create proxy instances for those interfaces." Base-interface methods "are routed into the base repository implementation of the store of your choice provided by Spring Data (for example, if you use JPA, the implementation is `SimpleJpaRepository`)." — [Spring Data JPA Reference 3.1.12](https://docs.spring.io/spring-data/jpa/docs/3.1.12/reference/html/)
- A repository's behavior is encoded in the **method name**: "Parsing query method names is divided into subject and predicate. The first part (`find…By`, `exists…By`) defines the subject of the query, the second part forms the predicate", conditions are concatenated "with `And` and `Or`", static ordering via an "`OrderBy` clause", plus `Distinct`, `IgnoreCase`, `Top`/`First`, and `_` for nested property traversal (`findByAddress_ZipCode`) — [Spring Data JPA Reference 3.1.12](https://docs.spring.io/spring-data/jpa/docs/3.1.12/reference/html/)
- Lookup strategy default is `CREATE_IF_NOT_FOUND`, which "looks up a declared query first, and, if no declared query is found, it creates a custom method name-based query" — [Spring Data JPA Reference 3.1.12](https://docs.spring.io/spring-data/jpa/docs/3.1.12/reference/html/)
- `@EnableJpaRepositories` activates repository scanning; "Without arguments, the package of the annotated class is scanned" — [Spring Data JPA Reference 3.1.12](https://docs.spring.io/spring-data/jpa/docs/3.1.12/reference/html/)
- DTOs are increasingly **records**: a record declaration is "a special kind of class" with a header of components; for each component the compiler generates a `private final` field and "a `public` accessor method with the same name and type" (e.g. `length()`), plus a canonical constructor, `equals`, `hashCode` and `toString` — [Oracle, Record Classes (Java SE 25)](https://docs.oracle.com/en/java/javase/25/language/records.html)

### Inferences
- The minimum role taxonomy a Spring-aware extractor needs, keyed on type-level annotations: `@SpringBootApplication` (entry), `@Configuration` + `@Bean` methods (wiring/infrastructure), `@RestController`/`@Controller` (HTTP surface), `@Service` (business logic), `@Repository` and Spring Data repository interfaces (persistence), `@Entity`/`@Table`/`@Embeddable` (the data model that maps to tables), records and plain POJOs in a `dto`/`payload` package (wire shapes), `@ControllerAdvice`/`@ExceptionHandler` (error surface), `@Component` (everything else managed).
- Because stereotypes are meta-annotations and composable, a literal-string annotation matcher is structurally incomplete: `@RestController` does not contain the text `@Controller`, and a project-local composed annotation (`@MyAppService` meta-annotated with `@Service`) will be invisible. A pragmatic extractor should (a) hard-code the known Spring set, and (b) resolve one extra level by scanning project `@interface` declarations for meta-annotations, marking anything unresolved as `assumed: true` rather than "no role".
- The repository case breaks the pipeline's core assumption outright: there is no function body, so brace matching returns an empty range, and "line range of the function" is a single line. The meaningful payload is the method *signature* plus the derived-query semantics of its name. An extractor that reports "0 functions, no implementation" for `UserRepository` is reporting the opposite of the truth — that file defines the entire data-access API of the app.
- `@Bean` methods inside `@Configuration` classes are a second place where the unit of meaning is a method, and where the method's **return type** is the thing being explained (it is the bean's type in the container), not its body.
- For a narrated video, the per-class "role" label is the single highest-value extracted field: it is what lets the script say "this is the service layer" rather than "this class has four methods".

### Gaps
- Could not fetch an authoritative Jakarta Persistence page for `@Entity`/`@Id`/`@GeneratedValue`/`@OneToMany`/`@JoinColumn`/`@Column` semantics within the call budget; the Spring Boot page confirms only that `@Entity` items are discovered by scanning from the main class's package. The report writer should treat the specific JPA annotation list here as well-known-but-uncited.
- Could not verify `@Query`, `@Param`, `@Modifying`, and repository `@Transactional` semantics — the Spring Data JPA reference page was truncated before those sections (sections 5.1.3 and 5.1.7 exist in its table of contents but their text was cut off). This matters: `@Query` means a repository method's name is *not* the query, which an extractor must detect.
- `application.properties` / `application.yml` precedence, profile-specific files, and relaxed binding to `@ConfigurationProperties` were not researched (no calls left). Noted as a known unit of meaning but uncited.

## How does a static analyzer handle Spring being an annotation/DI framework — and why is a "who imports this file" call graph misleading?

### Takeaway
In Spring, the edges of the architecture graph are **type-to-type resolutions performed by the container at runtime**, not call sites or imports in the source. A caller names an interface; the container picks the implementation by type, qualifier, or primary-ness. A naive import-based or name-based call graph will therefore attribute every service's behavior to the interface and show implementations as unreachable dead code.

### Cited Findings
- Injection is by **type**: "Make sure that your target components … are consistently declared by the type that you use for your `@Autowired`-annotated injection points. Otherwise, injection may fail due to a 'no type match found' error at runtime." — [Spring Framework, Using @Autowired](https://docs.spring.io/spring-framework/reference/core/beans/annotation-config/autowired.html)
- `@Autowired` is frequently **absent** on constructors: "An `@Autowired` annotation on such a constructor is not necessary if the target bean defines only one constructor." And: "If a class only declares a single constructor to begin with, it will always be used, even if not annotated." — [Spring Framework, Using @Autowired](https://docs.spring.io/spring-framework/reference/core/beans/annotation-config/autowired.html)
- Multi-constructor resolution is a runtime search: "The constructor with the greatest number of dependencies that can be satisfied by matching beans in the Spring container will be chosen. If none of the candidates can be satisfied, then a primary/default constructor (if present) will be used." — [Spring Framework, Using @Autowired](https://docs.spring.io/spring-framework/reference/core/beans/annotation-config/autowired.html)
- Injection points also include fields, setters, and "methods with arbitrary names and multiple arguments" — "You can apply `@Autowired` to fields as well and even mix it with constructors." — [Spring Framework, Using @Autowired](https://docs.spring.io/spring-framework/reference/core/beans/annotation-config/autowired.html)
- One injection point can mean **N beans**: an `@Autowired MovieCatalog[]`, a `Set<MovieCatalog>`, or a `Map<String, MovieCatalog>` receives all beans of that type — "the map values are all beans of the expected type, and the keys are the corresponding bean names." Ordering follows `Ordered`/`@Order`/`@Priority`, "otherwise, their order follows the registration order" — [Spring Framework, Using @Autowired](https://docs.spring.io/spring-framework/reference/core/beans/annotation-config/autowired.html)
- Ambiguity is resolved by annotations documented elsewhere: the page links to "Fine-tuning Annotation-based Autowiring with `@Primary` or `@Fallback`" and "…with Qualifiers", and states that self-references "do not participate in regular autowiring candidate selection and are therefore in particular never primary" — [Spring Framework, Using @Autowired](https://docs.spring.io/spring-framework/reference/core/beans/annotation-config/autowired.html)
- Injection can be optional, so a declared dependency may never be wired: with `required = false`, "A non-required field will not get populated at all in such cases, leaving its default value in place"; `Optional<MovieFinder>` and `@Nullable` parameters are alternatives — [Spring Framework, Using @Autowired](https://docs.spring.io/spring-framework/reference/core/beans/annotation-config/autowired.html)
- For `@Bean` factory methods the advice is to "declare the most specific return type on your factory method (at least as specific as required by the injection points referring to your bean)" — i.e. the **return type of a `@Bean` method is the graph edge** — [Spring Framework, Using @Autowired](https://docs.spring.io/spring-framework/reference/core/beans/annotation-config/autowired.html)
- Some dependencies are injected with no declaration anywhere: `BeanFactory`, `ApplicationContext`, `Environment`, `ResourceLoader`, `ApplicationEventPublisher`, `MessageSource` are "well-known resolvable dependencies" — [Spring Framework, Using @Autowired](https://docs.spring.io/spring-framework/reference/core/beans/annotation-config/autowired.html)
- Spring Data repository implementations **do not exist as source files at all** — Spring "create[s] proxy instances for those interfaces", routing base methods to `SimpleJpaRepository` — [Spring Data JPA Reference 3.1.12](https://docs.spring.io/spring-data/jpa/docs/3.1.12/reference/html/)
- Resolving a reference to a declaration in Java is exactly what a symbol solver is for, and it needs more than the file: JavaParser's `JavaSymbolSolver` is configured via `ParserConfiguration.setSymbolResolver(...)` with `TypeSolver`s — `ReflectionTypeSolver` (JDK/classloader), `JavaParserTypeSolver` (a source root), `JarTypeSolver` (a jar), `CombinedTypeSolver` — and unresolvable references throw `UnsolvedSymbolException`, ambiguous calls `MethodAmbiguityException` — [JavaParser symbol-resolution docs](https://tessl.io/registry/tessl/maven-com-github-javaparser--javaparser-core/3.27.0/files/docs/symbol-resolution.md)

### Inferences
- **Why "who imports this file" is wrong, concretely.** Take `OrderController` → `OrderService` (interface) → `OrderServiceImpl` (`@Service`) → `OrderRepository` (interface). The controller's `import` list and its constructor parameter both name `OrderService`. Nothing in the controller's source mentions `OrderServiceImpl`. An import-based graph therefore yields: `OrderController → OrderService` (an interface with no behavior to explain) and `OrderServiceImpl` with **zero inbound edges**, i.e. presented as dead code. The narration produced from that graph would be actively false — it would describe the app's main business logic class as unused. This is the headline failure mode: it is silent, plausible, and backwards.
- The same inversion hits repositories twice over: `OrderRepository` has no implementation file, so even a correct interface→impl resolution finds nothing; the real implementation is a runtime proxy over `SimpleJpaRepository`.
- A tractable approximation for a regex/heuristic pipeline, in descending reliability:
  1. **Bean index.** Scan every file for a type-level stereotype; record `simpleName`, FQN (from `package` + class name), the stereotype, and every `implements`/`extends` type in the declaration. This gives an interface→implementation map from the *implementation* side, which is where the information actually is.
  2. **Injection points.** For each stereotype-annotated class, parse the constructor whose name equals the class's simple name and extract its parameter *types* (not names). Also catch `@Autowired` fields and setters. Field-injection detection also needs `private final` fields that appear in the constructor parameter list — the common Lombok `@RequiredArgsConstructor` pattern generates the constructor, so **there may be no constructor in the source at all**; in that case the final fields *are* the injection points.
  3. **Edge resolution.** For each injected type, look it up in the bean index. If exactly one implementation exists → a confident edge. If several → emit all candidates and set `assumed: true` (this is precisely where `@Primary`/`@Qualifier` decide, and a regex pipeline cannot know which without reading those annotations).
  4. **Interface pass-through.** Where the injected type is an interface with exactly one implementation in the project, the narration should name the implementation, not the interface.
- `@Bean` methods must be indexed by **return type**, and `@Bean` method *parameters* are themselves injection points (Spring resolves them the same way) — so a `@Configuration` class is both a producer and a consumer of graph edges.
- Collection/`Map` injection and `@ConditionalOnProperty`/`@Profile`-gated beans mean the true graph is configuration-dependent. An honest tool reports a *candidate* graph with confidence, not a single resolved graph. For a video this is fine if the script says "resolved to OrderServiceImpl, the only implementation in this project".
- Runtime-only edges that no source-level analyzer can recover without modelling the framework: `@EventListener` / `ApplicationEventPublisher` pub-sub, `@Scheduled` methods (invoked by the container, caller = nobody), AOP `@Aspect` advice, `@Transactional` proxying (the method you see is wrapped), `@RequestMapping` handlers themselves (invoked by the dispatcher). Every one of these has **zero in-project callers** and must be explicitly labelled "invoked by the Spring container" rather than "unused".
- The nearest analogue to "event handlers" in the pipeline's existing TS schema is this set: `@EventListener`, `@Scheduled`, `@KafkaListener`/`@RabbitListener`/`@JmsListener`, `@ExceptionHandler`, and `@PostConstruct`/`@PreDestroy` lifecycle hooks. Mapping them onto the existing `eventHandlers` field is the cheapest way to make the Spring extractor fit the existing JSON schema.

### Gaps
- `@Qualifier` / `@Primary` / `@Fallback` exact selection rules are documented on pages linked from the `@Autowired` page, which were not fetched; the precedence order between them is therefore uncited here.
- No source found within budget for a published Spring-specific DI-graph static analyzer (e.g. Spring's own `BeanDefinition` tooling, Spring Tools/STS indexing, or Archunit-style approaches). Whether an off-the-shelf Python-usable Spring bean-graph extractor exists is unresolved — I found none.

## How are HTTP routes declared, and why would a per-method regex report the wrong path?

### Takeaway
The effective URL of a Spring handler is the **class-level `@RequestMapping` path concatenated with the method-level mapping path**. A regex that scans only method-level `@GetMapping("/{id}")` annotations reports `/{id}` instead of `/persons/{id}` — a wrong answer, not a missing one, for essentially every controller in a real project.

### Cited Findings
- "You can use it at the class level to express shared mappings or at the method level to narrow down to a specific endpoint mapping." — [Spring Framework, Mapping Requests](https://docs.spring.io/spring-framework/reference/7.0/web/webflux/controller/ann-requestmapping.html)
- The official example states the combined paths explicitly in comments: with `@RequestMapping("/persons")` on the class, `@GetMapping("/{id}")` is "effectively /persons/{id}" and a bare `@PostMapping` (no path argument) is "effectively /persons" — [Spring Framework, Mapping Requests](https://docs.spring.io/spring-framework/reference/7.0/web/webflux/controller/ann-requestmapping.html)
- The docs' own caveat: the page states the class-level/method-level rule in prose only as "shared mappings"/"narrow down"; the concatenation itself is shown by example. (Noted as a documentation weakness rather than ambiguity in behavior.) — [Spring Framework, Mapping Requests](https://docs.spring.io/spring-framework/reference/7.0/web/webflux/controller/ann-requestmapping.html)
- Shortcut variants: "There are also HTTP method specific shortcut variants of `@RequestMapping`: `@GetMapping`, `@PostMapping`, `@PutMapping`, `@DeleteMapping`, `@PatchMapping`" — all "examples of composed annotations". Rationale: "a `@RequestMapping` is still needed at the class level to express shared mappings." Plain `@RequestMapping` "by default, matches to all HTTP methods" — [Spring Framework, Mapping Requests](https://docs.spring.io/spring-framework/reference/7.0/web/webflux/controller/ann-requestmapping.html)
- `@GetMapping` "support[s] HTTP HEAD transparently for request mapping purposes" — one annotation, two methods served — [Spring Framework, Mapping Requests](https://docs.spring.io/spring-framework/reference/7.0/web/webflux/controller/ann-requestmapping.html)
- Only one mapping annotation per element: `@RequestMapping` "cannot be used in conjunction with other `@RequestMapping` annotations that are declared on the same element (class, interface, or method)"; if several are found "a warning will be logged, and only the first mapping will be used" — [Spring Framework, Mapping Requests](https://docs.spring.io/spring-framework/reference/7.0/web/webflux/controller/ann-requestmapping.html)
- Path pattern syntax a route extractor must normalize: `?` "Matches one character"; `*` "Matches zero or more characters within a path segment"; `**` "Matches zero or more path segments"; `{name}` "captures the path segment as a variable named 'name'"; `{name:[a-z]+}` "Matches the regexp `[a-z]+` as a path variable named 'name'"; `{*path}` captures trailing segments. Restrictions: "only a single `**`/`{*path}` instance is allowed per pattern", `"/resources/**/file.png"` is invalid, and `{*path}` cannot appear mid-path — [Spring Framework, Mapping Requests](https://docs.spring.io/spring-framework/reference/7.0/web/webflux/controller/ann-requestmapping.html)
- Paths can be **non-literal**: "Embedded `${…}` placeholders" are "resolved on startup via `PropertySourcesPlaceholderConfigurer`", and SpEL `#{…}` expressions are supported — [Spring Framework, Mapping Requests](https://docs.spring.io/spring-framework/reference/7.0/web/webflux/controller/ann-requestmapping.html)
- `@PathVariable`: "Captured URI variables can be accessed with `@PathVariable`", e.g. `@GetMapping("/owners/{ownerId}/pets/{petId}") public Pet findPet(@PathVariable Long ownerId, @PathVariable Long petId)`. "URI variables are automatically converted to the appropriate type or a `TypeMismatchException` is raised." Names "can be named explicitly (for example, `@PathVariable("customId")`), but you can leave that detail out if the names are the same and you compile your code with the `-parameters` compiler flag." — [Spring Framework, Mapping Requests](https://docs.spring.io/spring-framework/reference/7.0/web/webflux/controller/ann-requestmapping.html)
- Query parameters appear in **two different roles**. As a mapping *condition*: "You can narrow request mappings based on query parameter conditions. You can test for the presence of a query parameter (`myParam`), for its absence (`!myParam`), or for a specific value (`myParam=myValue`)" — this is the `params` attribute, not `@RequestParam`. (The page documents `@RequestParam`/`@RequestBody` binding only by link; `@RequestBody` appears in examples, e.g. `@PostMapping(path = "/pets", consumes = "application/json") public void addPet(@RequestBody Pet pet)`.) — [Spring Framework, Mapping Requests](https://docs.spring.io/spring-framework/reference/7.0/web/webflux/controller/ann-requestmapping.html)
- `consumes` and `produces` behave **opposite to path**: "when used at the class level, a method-level `consumes` attribute overrides rather than extends the class-level declaration", and identically for `produces` ("overrides rather than extend"). Negation is supported (`!text/plain`) — [Spring Framework, Mapping Requests](https://docs.spring.io/spring-framework/reference/7.0/web/webflux/controller/ann-requestmapping.html)
- `@HttpExchange`/`@GetExchange`/`@PostExchange` is an alternative on interfaces that a controller can implement, so the mapping may live on an **interface, not the class**: the example has `@HttpExchange("/persons")` on `interface PersonService` and `class PersonController implements PersonService`. Difference: "`@RequestMapping` can map to any number of requests by path patterns, HTTP methods, and more, while `@HttpExchange` declares a single endpoint" — [Spring Framework, Mapping Requests](https://docs.spring.io/spring-framework/reference/7.0/web/webflux/controller/ann-requestmapping.html)
- Suffix matching differs by stack: "Spring WebFlux does not support suffix pattern matching — unlike Spring MVC, where a mapping such as `/person` also matches to `/person.*`" — [Spring Framework, Mapping Requests](https://docs.spring.io/spring-framework/reference/7.0/web/webflux/controller/ann-requestmapping.html)

### Inferences
- **Required extraction algorithm**, minimum viable: (1) find the type declaration and its annotations; (2) if a class-level `@RequestMapping` exists, extract its path (from `value =`, `path =`, or the bare single-string form, and handle the array form `{"/a","/b"}` which multiplies the routes); (3) for each method-level mapping annotation, extract its path or treat absence-of-path as empty; (4) join with exactly one `/`, collapsing doubles and handling the empty-method-path case (`/persons` + `` → `/persons`, not `/persons/`); (5) derive the HTTP verb from the annotation name, or from `method =` for plain `@RequestMapping`, or "ALL VERBS" when neither is present.
- **Silent-wrongness inventory for routes** (all produce confidently incorrect output, not an error): missing class-level prefix; bare `@PostMapping` with no argument producing an empty/absent route; array-valued paths reported as one literal string containing braces; `${…}`/`#{…}` placeholders reported verbatim as if they were the URL; `@GetMapping` not reported as also serving HEAD; mappings inherited from an `@HttpExchange` interface reported as "no routes in this controller"; a class-level `produces` silently assumed to apply when a method overrode it.
- `{name:[a-z]+}` is the single nastiest literal for a regex extractor: the regex *inside* the path pattern contains brackets, braces and quantifiers, and a naive `\{(\w+)\}` variable-name capture misses it entirely while a naive `\{([^}]+)\}` yields `name:[a-z]+` as the variable name. Variable names must be split on the first `:`.
- The route table is the highest-value artifact for the video: for a Spring Boot app, "here are the 14 endpoints this app exposes, with verb, full path, path variables, request body type and response type" is the single most comprehensible opening frame, and every one of those fields is recoverable statically with the algorithm above.
- Parameter annotations to extract per handler, mapping to the pipeline's existing fields: `@PathVariable` (name, Java type, explicit-name override), `@RequestParam` (name, `required`, `defaultValue`), `@RequestBody` (the DTO type — this is the link from the route to the data model), `@RequestHeader`, `@CookieValue`, `@Valid`/`@Validated`, plus the method's **return type** (`ResponseEntity<Foo>`, `List<Foo>`, `Page<Foo>`) as the response shape. Note `@RequestParam` vs the mapping-level `params` attribute are different things and must not be conflated.
- `@RestController` vs `@Controller` must be distinguished in narration: the former implies `@ResponseBody` on every method (JSON out), the latter implies a view name is returned (server-rendered template) — an explanation that gets this backwards misdescribes what the endpoint returns.

### Gaps
- The MVC (servlet) version of the request-mapping page was blocked; findings above come from the WebFlux mirror of the same reference chapter. The two differ on suffix pattern matching (explicitly noted on the page itself) and WebFlux uses `PathPattern`/`PathPatternParser`. For a Spring **MVC** project the MVC page should be re-checked; the class/method concatenation rule and all annotation names are identical.
- `@RequestParam` and `@RequestBody` binding details (`required`, `defaultValue`, converters) are documented on separate pages not fetched here.
- `server.servlet.context-path` (and `spring.webflux.base-path`) prepend a further prefix from `application.properties`, which would make even a correctly concatenated path incomplete. Not verified against a source — flagged as a likely additional silent error.

## Visibility in Java vs TS `export` vs Go's capital-letter rule

### Takeaway
Java visibility is a **per-member keyword** (`public`/`protected`/package-private/`private`), orthogonal to naming and to file structure; the pipeline's two existing heuristics are both wrong for Java, and the Go capital-letter rule is catastrophically wrong because *every* Java class name is capitalized by convention while method visibility is independent of case.

### Cited Findings
- Visibility is not inferable from annotation presence or role: Spring explicitly notes "an annotated constructor does not have to be public" — a `private` or package-private constructor can still be the injection point — [Spring Framework, Using @Autowired](https://docs.spring.io/spring-framework/reference/core/beans/annotation-config/autowired.html)
- Record components generate `private final` fields with `public` accessors of the same name — so the same identifier exists at two visibilities in one declaration — [Oracle, Record Classes](https://docs.oracle.com/en/java/javase/25/language/records.html)
- A record class "is implicitly `final`", and nested records "are implicitly static" — modifiers can be implicit and absent from the source text — [Oracle, Record Classes](https://docs.oracle.com/en/java/javase/25/language/records.html)
- Interface methods in Spring Data repositories carry no modifier at all in the source (`User findByEmailAddress(EmailAddress emailAddress);`) yet are implicitly `public` — [Spring Data JPA Reference 3.1.12](https://docs.spring.io/spring-data/jpa/docs/3.1.12/reference/html/)

### Inferences
- Concrete failures of the Go rule applied to Java: `UserService` (capital, but may be package-private), `private void validate()` (lowercase → correctly "not exported" by accident), `public void save()` (lowercase → reported as internal, **wrong**), `public static final int MAX` (uppercase constant, correct by accident). The rule is uncorrelated with the truth for methods and fields, and correlated only by accident for types.
- Concrete failures of the TS `export` rule: the token `export` never appears in Java, so an `export`-prefix test marks **every Java declaration as not exported**. If the pipeline falls back to "not exported ⇒ don't explain", a Spring file yields an empty explanation.
- The correct rule is a modifier scan on the declaration line, with four defaults that are easy to get wrong:
  - **Absent modifier means different things in different contexts.** On a class/method/field in a class body it is *package-private*. On an **interface** member it is implicitly `public` (and interface fields are `public static final`). On an **enum** constant it is implicitly `public static final`. A single "no modifier ⇒ package-private" rule mislabels every repository method and every interface in the project.
  - Modifier order is not fixed and annotations interleave: `@Override public final synchronized <T> List<T> foo(...)`, `public static <T extends Comparable<T>> T max(...)`. A regex anchored on `^\s*(public|private|protected)\s+\w+\s+\w+\(` fails on generics, on annotations placed on the same line, and on `static`/`final`/`synchronized`/`abstract`/`default`/`native`/`transient`/`volatile` appearing before or after the access modifier.
  - Lombok (`@Getter`, `@Setter`, `@Data`, `@Builder`, `@RequiredArgsConstructor`, `@Value`) creates public members that **do not appear in the source at all**. A file using `@Data` has a public API far larger than its text. This should be flagged in output, not silently omitted.
- **What the tool should report as "the public surface"**, for explanation purposes, is not raw `public`-ness but *framework reachability*, in this priority order: (1) HTTP endpoints (handler methods and their full paths) — the app's actual external API; (2) bean types registered by stereotype, plus their `public` methods, which are the surface other beans can call; (3) repository query methods; (4) `@Bean` method return types; (5) `public` members of entities/DTOs as the data contract. A plain `public` filter would include thousands of getters and exclude nothing interesting; framework reachability is the signal a viewer cares about.
- One field is worth emitting alongside visibility: `isFrameworkEntryPoint` (true for handler methods, `@Scheduled`, `@EventListener`, listeners, `main`). These are `public` but have no in-project caller, and conflating them with unused public methods is the same error as the DI-graph failure above.

### Gaps
- No citation fetched for the JLS §6.6 access-control rules or for the implicit-`public` rule on interface members; these are uncontroversial Java facts but are uncited in these notes.

## Javadoc vs JSDoc, and whether a `//` / `/* */` extractor picks it up

### Takeaway
A doc-comment extractor written for JSDoc will *mostly* work on Javadoc — both are `/** … */` immediately before a declaration with `@tag` block tags — but it will get the details wrong in four specific ways: leading-asterisk stripping, `{@inline}` tags, Javadoc's `@param <T>` type-parameter form, and the inheritance rule where a method's real documentation lives on a supertype. Crucially, a naive `/* */` matcher cannot distinguish a doc comment from an ordinary block comment or a license header.

### Cited Findings
- Form and placement: "Documentation comments are recognized only when placed immediately before the declaration of a module, package, class, interface, constructor, method, enum member, or field." Also: "Documentation comments placed in the body of a method are ignored. Only one documentation comment per declaration statement is recognized." — [Oracle, Documentation Comment Specification (JDK 22)](https://docs.oracle.com/en/java/javase/22/docs/specs/javadoc/doc-comment-spec.html)
- Structure: "an initial main description, followed by a series of block tags"; "The main description… is the content from the beginning of the comment, up to the first block tag… The main description cannot continue after any block tags." "It is possible to have a comment with only block tags and no main description." — [Oracle, Doc Comment Spec](https://docs.oracle.com/en/java/javase/22/docs/specs/javadoc/doc-comment-spec.html)
- Asterisk stripping: "When a documentation comment is read, leading asterisks (`*`) on each line are discarded, and blanks and tabs that precede the initial asterisks (`*`) are also discarded." But: "If you omit the leading asterisk on a line, then the leading whitespace is no longer removed so that you can paste code examples directly into a documentation comment inside a `<pre>` tag with its indentation preserved." — [Oracle, Doc Comment Spec](https://docs.oracle.com/en/java/javase/22/docs/specs/javadoc/doc-comment-spec.html)
- Block tags: "Block tags are of the form `@`*identifier* *content*", and "Each block tag must appear at the beginning of a line, ignoring leading asterisks, whitespace characters, and the initial comment delimiter (`/**`)." A literal leading `@` requires `&#064;` or `@@`. — [Oracle, Doc Comment Spec](https://docs.oracle.com/en/java/javase/22/docs/specs/javadoc/doc-comment-spec.html)
- Inline tags: "Inline tags are of the form `{@`*identifier* *content*`}`", braces must be balanced, and "Lines beginning with `@` that are enclosed within an inline tag are not considered as beginning a block tag." — [Oracle, Doc Comment Spec](https://docs.oracle.com/en/java/javase/22/docs/specs/javadoc/doc-comment-spec.html)
- `@param` has **two forms**: `@param` *parameter-name* *description* and `@param <`*type-parameter-name*`>` *description* (e.g. `@param <E> Type of element stored in a list`). "This tag is valid only in a documentation comment for a method, constructor, or class." For inherited docs the match uses "the parameter's position, not the parameter's name." — [Oracle, Doc Comment Spec](https://docs.oracle.com/en/java/javase/22/docs/specs/javadoc/doc-comment-spec.html)
- `@return` has a block form and, since JDK 16, an inline form `{@return` *description*`}` that "may only occur at the beginning of a method's main description". It is "valid only in a documentation comment for a method" and required when the return type is not `void`. — [Oracle, Doc Comment Spec](https://docs.oracle.com/en/java/javase/22/docs/specs/javadoc/doc-comment-spec.html)
- `@throws` *exception-name* *description* is the recommended form; `@exception` is "equivalent to this tag, although the `@throws` form is now recommended." — [Oracle, Doc Comment Spec](https://docs.oracle.com/en/java/javase/22/docs/specs/javadoc/doc-comment-spec.html)
- `{@link reference label}` "Inserts an inline link with a visible text label"; `{@code text}` "Displays *text* in code font without interpreting the text as HTML markup or nested Javadoc tags", e.g. `{@code A<B>C}` displays as `A<B>C`. — [Oracle, Doc Comment Spec](https://docs.oracle.com/en/java/javase/22/docs/specs/javadoc/doc-comment-spec.html)
- Documentation can be **absent from the file and inherited**: `{@inheritDoc}` "Indicates that a method documentation comment part that contains this tag is the same as that of the overridden method in a superclass or superinterface", and "a missing item is considered as if it were provided with `{@inheritDoc}` as its content" when the declaration is overriding. Escape sequences "cannot be used in inline tags that contain literal text; this includes `{@code}`, `{@literal}`, `{@snippet}`". — [Oracle, Doc Comment Spec](https://docs.oracle.com/en/java/javase/22/docs/specs/javadoc/doc-comment-spec.html)
- Javadoc permits embedded HTML (the spec references `<pre>` tags, HTML entities such as `&#125;`, `&lbrace;`, `&rbrace;`, and `<code>` equivalence for `{@code}`) — [Oracle, Doc Comment Spec](https://docs.oracle.com/en/java/javase/22/docs/specs/javadoc/doc-comment-spec.html)

### Inferences
- **What a JSDoc-shaped extractor gets right on Java:** the `/** … */` delimiter, "immediately preceding the declaration", one comment per declaration, `@param name description`, `@return description`, `@throws`/`@exception`, `@deprecated`, `@see`. The overall shape transfers.
- **What it gets wrong:**
  - **Type-annotated `@param`.** JSDoc writes `@param {string} name - desc`; Javadoc writes `@param name desc` with the type taken from the signature. A JSDoc-trained regex expecting a `{Type}` group either fails to capture the name or captures nothing. Conversely, Javadoc's legitimate `@param <E> desc` form looks exactly like a JSDoc type brace and will be mis-parsed as `name = "<E>"`-less with the description eaten.
  - **Asterisk stripping must be per-line and conditional.** Strip `^\s*\*\s?` only when the asterisk is present; preserve indentation on lines that lack it (the spec says so explicitly, for `<pre>` blocks). Stripping all leading whitespace unconditionally destroys embedded code examples — which is precisely the content a code-explanation video would want to narrate.
  - **Inline tags are not block tags.** `@` inside `{@…}` must not terminate the main description, and the spec says as much. A line-oriented `^@(\w+)` block-tag splitter will split in the middle of `{@link org.Foo#bar()\n @see …}`-style wrapped inline tags. Inline tags should be flattened for narration: `{@code X}` → `X`, `{@link Foo#bar()}` → `Foo.bar()`, `{@literal …}` → text.
  - **Embedded HTML must be stripped before TTS.** Javadoc bodies legitimately contain `<p>`, `<pre>`, `<ul>`, `<li>`, `&amp;`, `&#064;`. Feeding these to a narration script produces spoken markup. JSDoc bodies are usually markdown, so a JSDoc pipeline will have no HTML-stripping step.
  - **Inheritance means an empty doc comment is not an undocumented method.** A one-line `@Override` method with `{@inheritDoc}` or with no doc comment at all may be fully documented on an interface in another file. Reporting "undocumented" is wrong; reporting "documented on the supertype" needs cross-file resolution, which a per-file regex pass cannot do. Mark `assumed: true`.
- **The comment-type discrimination problem a `//` + `/* */` extractor has:** `/** … */` (doc), `/* … */` (ordinary block), `/*- … */` and `/*\n * Copyright …*/` (license headers, nearly always the first thing in a Java file) are all matched by a generic `/\*[\s\S]*?\*/`. In Java this is far more damaging than in TS, because essentially every corporate Java file opens with an Apache/proprietary license block comment. A generic extractor will attach the license text as the "leading doc comment" of the first declaration — i.e. the class-level explanation for every file becomes a license notice. The discriminator is cheap and must be applied: the comment must start with exactly `/**` (and `/**/` is the empty block comment, not a doc comment), and must be separated from the declaration only by whitespace and annotations.
- **Annotations sit between the doc comment and the declaration.** `/** … */ @RestController @RequestMapping("/x") public class Foo` — a "comment must be on the line immediately above the declaration" rule (common in TS extractors, where decorators are rarer) fails here. The extractor must skip over any number of annotation lines, including annotations with multi-line parenthesized arguments.

### Gaps
- None material; the JDK spec answered this question directly.

## Java syntax that breaks brace matching and regex extraction

### Takeaway
Brace matching is *structurally* sound in Java (the language is brace-delimited) but is defeated by braces appearing inside string literals, char literals, comments, annotation arguments, and text blocks; while the *identification* of what a brace-delimited block belongs to is defeated by generics, multi-line annotations, overloads, lambdas, nested types, and the several declaration forms that have no body at all.

### Cited Findings
- **Annotations carry parenthesized arguments, including arrays and nested annotations**, which routinely span lines: `@ComponentScan(basePackages = "org.example")`, `@Service @SessionScope(proxyMode = ScopedProxyMode.INTERFACES)`, and annotation-type declarations such as `@Target(ElementType.TYPE) @Retention(RetentionPolicy.RUNTIME) @Documented @Component public @interface Service { }` — [Spring Framework, Classpath Scanning](https://docs.spring.io/spring-framework/reference/7.1/core/beans/classpath-scanning.html)
- Annotation arguments can contain route patterns with braces and regex: `@GetMapping("/{id}")`, `{name:[a-z]+}`, `{*path}`, and SpEL `#{…}` / property `${…}` placeholders — all **brace characters inside a string inside an annotation above a declaration** — [Spring Framework, Mapping Requests](https://docs.spring.io/spring-framework/reference/7.0/web/webflux/controller/ann-requestmapping.html)
- **Generics in signatures and in annotations**: `public interface List<E> extends Collection<E>`, `<T, V extends T> V convert(String string, Class<T> type)` — the method's return type and type parameters both contain angle brackets before the method name — [Oracle, Doc Comment Spec](https://docs.oracle.com/en/java/javase/22/docs/specs/javadoc/doc-comment-spec.html)
- `{@code A<B>C}` is documented as displaying unchanged — i.e. angle brackets and braces legitimately appear inside comments — [Oracle, Doc Comment Spec](https://docs.oracle.com/en/java/javase/22/docs/specs/javadoc/doc-comment-spec.html)
- **Interface and abstract methods have no body**: `User findByEmailAddress(EmailAddress emailAddress);` and `CrudRepository`'s methods have "no bodies, only semicolons" — [Spring Data JPA Reference 3.1.12](https://docs.spring.io/spring-data/jpa/docs/3.1.12/reference/html/)
- **Records**: the declaration can be body-less (`record Rectangle(double length, double width) { }`); a **compact constructor** has the form `public Rectangle { … }` with *no parameter list*; records may contain static fields, static initializers, static methods, instance methods, and nested classes/interfaces/records ("nested records… are implicitly static"); instance variables and instance initializers are forbidden; records can `implements` an interface but never `extends` — [Oracle, Record Classes](https://docs.oracle.com/en/java/javase/25/language/records.html)
- Static initializer blocks exist and look like a nameless body: `static { goldenRatio = (1 + Math.sqrt(5)) / 2; }` — [Oracle, Record Classes](https://docs.oracle.com/en/java/javase/25/language/records.html)

### Inferences
Concrete breakages, each with the symptom a regex-and-brace pipeline produces:

1. **Braces inside string and char literals.** `"/{id}"`, `"{\"k\":1}"`, `'{'`, `'}'`, `String.format("Invalid dimensions: %f, %f", …)`. A brace counter that does not tokenize strings closes the body early or never. Java also has **text blocks** (`"""` … `"""`, since Java 15), which commonly hold JSON and SQL full of braces and quotes, and inside which `\` escapes behave differently. Symptom: a method's reported line range ends mid-method or swallows the rest of the file. Silent.
2. **Braces inside comments**, including Javadoc `{@code}`/`{@link}` and commented-out code. Symptom: same as above.
3. **Generics with angle brackets.** `Map<String, List<Pair<K, V>>>`, `ResponseEntity<Page<OrderDto>>`, `<T extends Comparable<? super T>> void sort(List<T> l)`. Angle brackets do not nest-match reliably (`>>` is also a shift operator; `List<List<String>>` closes with `>>`). A signature regex keyed on `\w+\s+\w+\s*\(` misses the return type entirely; one keyed on commas in the parameter list splits `Map<String, Integer> m` into two bogus parameters. Symptom: wrong parameter lists and wrong return types on DTO-heavy Spring code — i.e. wrong request/response shapes in the narration.
4. **Multi-line annotations with parenthesized arguments.** `@RequestMapping(value = {"/a", "/b"}, method = RequestMethod.GET, produces = MediaType.APPLICATION_JSON_VALUE)` wrapped across four lines; `@Table(name = "orders", indexes = @Index(columnList = "customer_id"))`; `@PreAuthorize("hasRole('ADMIN')")`. Symptom: a line-oriented annotation regex captures a truncated path, and a "comment immediately above declaration" rule fails. Note the array form `{"/a","/b"}` contains braces *before* the method body — a brace counter that starts at the annotation rather than the signature opens a phantom block.
5. **Overloaded methods.** `save(Order o)` and `save(Order o, boolean flush)` share a name. Any map keyed on method name collapses them, and a "find the function named save" lookup resolves arbitrarily. Symptom: one of the two is dropped from the explanation, or their line ranges are merged. Java also permits a field, a method and a nested type to share a name.
6. **Inner, nested, static nested, local and anonymous classes.** `new ResponseEntity<>(…) { … }`, `Comparator<Order> c = new Comparator<>() { public int compare(…) { … } };`, `private static class Row { … }` inside a service. Symptom: the anonymous class's `compare` is reported as a top-level method of the file; the nesting depth is lost, so "this file defines 9 classes" when it defines 1 with 8 helpers. Also, a brace counter walking the outer class body will encounter these and, if it only counts to the *first* closing brace at depth 1, truncate.
7. **Lambdas and method references.** `list.forEach(o -> { total += o.amount(); });`, `.map(OrderMapper::toDto)`, `Function<A,B> f = a -> { … }`. Lambda bodies are brace-delimited blocks that are *not* methods. Symptom: inflated function counts and nonsense "function" entries; `->` also breaks naive signature regexes. Switch expressions with arrow labels (`case A -> { … }`) add more of the same.
8. **Interfaces with `default` and `static` methods.** `default List<Order> findAllActive() { return findByActive(true); }` inside an interface — an interface member that *does* have a body, next to members that don't. Symptom: a rule like "interface ⇒ no bodies" drops real logic; a rule like "every method has a body" hangs/overruns on the abstract ones. For Spring this is where repository-level shared logic hides.
9. **Abstract methods and the body-less declaration generally.** `abstract void process();`, `native` methods, and every Spring Data query method. A brace matcher that assumes the next `{` after a signature belongs to that signature will attach the *following* method's body to it. Symptom: every method's line range shifted by one method — systematically wrong, never an error.
10. **Enums with bodies.** `enum Status { ACTIVE("A") { @Override boolean isOpen() { return true; } }, CLOSED("C"); private final String code; Status(String c){…} abstract boolean isOpen(); }` — constants with per-constant class bodies, a constructor, fields, abstract methods, and a `;` separating constants from members. Symptom: constants parsed as methods, the constructor parsed as a method named after the enum, and brace depth that a simple counter handles but a simple *classifier* does not. Spring code uses enums heavily for status fields on entities.
11. **Records.** The compact constructor `public Rectangle { … }` has no parentheses, so a signature regex requiring `(` misses it; the record header `record Rectangle(double length, double width)` looks like a method declaration (name + parameter list) to a regex looking for methods; and the generated accessors (`length()`, `width()`) exist nowhere in the source. Symptom: a DTO record is reported as having zero members, or its header is reported as a function.
12. **Annotations on types inside signatures, varargs, arrays.** `void f(@NotNull String... names)`, `int[] a`, `String args[]` (C-style, still legal). Minor but each breaks a tightened parameter regex.
13. **Sealed types and `permits`**, plus the contextual keywords `record`, `sealed`, `permits`, `yield`, `var` — none are reserved words, so `int record = 5;` and a variable named `var` are legal. A keyword-anchored regex can match an identifier.
14. **Multiple top-level types per file** (one `public`, others package-private) and the fact that the `public` type must match the filename. Symptom: "the class in this file" is ambiguous.

Practical mitigations short of a full parser:
- **Lex before you match.** A ~100-line Python pre-pass that replaces the contents of string literals, char literals, text blocks, and all comments with same-length filler makes brace matching correct and makes every subsequent regex dramatically safer. This is the single highest-value change and is cheap.
- Record the annotation block as a separate span attached to the declaration, parsed with a paren-balanced scanner (not a line regex).
- Key methods on `(name, arity, parameter-type-list)`, never on name alone.
- Track brace depth to distinguish top-level members from nested-type and lambda bodies; emit a `nestingDepth` and `enclosingType` field.
- Treat "no `{` before the next `;`" as the body-less case explicitly, and emit `hasBody: false` rather than guessing a range.
- Even with all of this, **prefer an actual parser** (next section). The mitigations above are for a pipeline that cannot change its architecture.

### Gaps
- Text blocks, sealed classes/`permits`, and switch-expression arrow syntax were asserted from general Java knowledge; within the call budget I did not fetch JLS citations for them. The record and compact-constructor claims are cited.

## Package/directory layout, src/main/java vs src/test/java, and chunking

### Takeaway
Spring Boot projects are Maven/Gradle-standard: `src/main/java/<reversed-domain>/…` with sibling role packages (`controller`, `service`, `repository`, `model`/`entity`, `dto`, `config`), and `src/test/java` mirroring it. The directory a file sits in is a strong, free prior on its role — and `src/test/java` should be excluded from (or separated in) the explanation, since test files would otherwise dominate the file count while explaining nothing about the application.

### Cited Findings
- "We recommend that you follow Java's recommended package naming conventions and use a reversed domain name (for example, `com.example.project`)." The default package "can cause particular problems for Spring Boot applications that use the `@ComponentScan`, `@ConfigurationPropertiesScan`, `@EntityScan`, or `@SpringBootApplication` annotations, since every class from every jar is read." — [Spring Boot, Structuring Your Code](https://docs.spring.io/spring-boot/3.5.0/reference/using/structuring-your-code.html)
- "We generally recommend that you locate your main application class in a root package above other classes… Using a root package also allows component scan to apply only on your project." — [Spring Boot, Structuring Your Code](https://docs.spring.io/spring-boot/3.5.0/reference/using/structuring-your-code.html)
- The reference's own recommended layout is **feature-sliced, not layer-sliced** — `com/example/myapplication/MyApplication.java`, then `customer/{Customer, CustomerController, CustomerService, CustomerRepository}.java` and `order/{Order, OrderController, OrderService, OrderRepository}.java` — [Spring Boot, Structuring Your Code](https://docs.spring.io/spring-boot/3.5.0/reference/using/structuring-your-code.html)
- Spring's own examples use `@ComponentScan(basePackages = "org.example")` with Ant-style patterns like `"org.example.**"` and comma/semicolon/space-separated lists, confirming that scan roots are configurable and may not match the directory tree — [Spring Framework, Classpath Scanning](https://docs.spring.io/spring-framework/reference/7.1/core/beans/classpath-scanning.html)
- Kotlin Spring Boot projects exist with the same structure (`src/main/kotlin`), with the entry point as a top-level `fun main` plus `runApplication<MyApplication>(*args)` — relevant if the pipeline auto-detects "a JVM Spring project" by directory — [Spring Boot, Structuring Your Code](https://docs.spring.io/spring-boot/3.5.0/reference/using/structuring-your-code.html)

### Inferences
- Detection of "this is a Spring Boot project": presence of `pom.xml` or `build.gradle`/`build.gradle.kts` + `src/main/java`, and a file containing `@SpringBootApplication`. Also `src/main/resources/application.properties` or `application.yml`. The entry file found this way should be chunk #1.
- **Layer-sliced vs feature-sliced matters for chunking and narration.** Many real projects use `controller/`, `service/`, `repository/`, `model/` (the layout the question names); Spring's own recommendation is feature slices (`customer/`, `order/`). A chunker should detect which, because the natural video outline differs: layer-sliced → narrate layer by layer; feature-sliced → narrate feature by feature, walking the four files of each slice together. Detect by checking whether the directory names under the root package match the known layer vocabulary.
- The directory name is a cheap prior but must **lose to the annotation** when they disagree (a `@Service` in `util/` is a service). Report the annotation-derived role as authoritative and the path-derived role as corroboration.
- `src/test/java` handling: exclude from the main explanation by default; it is a separate source root, its classes carry `@SpringBootTest`/`@WebMvcTest`/`@DataJpaTest`/`@Test`/`@MockBean`, and including it roughly doubles file count while adding no architecture. Optionally mine it for **one** high-value thing: the `@WebMvcTest` MockMvc calls spell out concrete request/response examples for endpoints, which make excellent narration. `src/main/resources` (templates, static, `application*.yml`, `db/migration` Flyway SQL) is a third source root worth a short dedicated chunk.
- **Chunking recommendation for a Spring project**, replacing per-file-by-line-count chunking:
  - Chunk by **bean/type**, one chunk per annotated type, since the type is the unit of meaning. Typical Spring classes are 50–300 lines, comfortably within the pipeline's "small/medium" bands.
  - Group a feature slice's controller + service + repository + entity + DTO into one **narrative section** with 3–5 chunks, so the video can trace a request end-to-end — which is the only ordering in which a DI-heavy app makes sense.
  - Give the entry class and the `@Configuration`/`application.yml` pair their own short chunks regardless of line count (they are short but load-bearing).
  - For repository interfaces, chunk the whole interface as one unit (there are no bodies to split) and narrate the derived query method names.
  - Oversized classes to expect splitting: a fat `@RestController` with 15 handlers (split by endpoint group), a `@Configuration` with many `@Bean`s (split by concern), and an `@Entity` with many relationships (keep whole — the relationship set is the point).

### Gaps
- Could not cite the Maven Standard Directory Layout page itself within budget; the `src/main/java` / `src/test/java` convention is asserted from general knowledge, with the Spring Boot page confirming only the package layout under it.

## Which tools parse Java well, and what are the realistic options for a Python pipeline?

### Takeaway
For a **Python** pipeline the realistic, maintained choice is **tree-sitter with the `tree-sitter-java` grammar** (a C grammar with first-class Python bindings): it gives a real CST with node types and byte ranges, is error-tolerant, and solves every lexical problem listed above. `javalang` is a pure-Python alternative but is old and Java-7/8-era. Everything else that parses Java *well* — JavaParser, Eclipse JDT, Spoon — is a JVM library, usable from Python only by running a JVM sidecar, which is the right call only if you need **type and symbol resolution**, which is exactly what the Spring DI graph wants.

### Cited Findings
- JavaParser's symbol solver is what turns a syntax tree into resolved references: you set a `SymbolResolver` via `ParserConfiguration.setSymbolResolver(...)`, typically `JavaSymbolSolver(typeSolver)`; then `nameExpr.resolve()`, `methodCall.resolve()` and `expr.calculateResolvedType()` work. `SymbolResolver.resolveDeclaration(...)` resolves a `MethodCallExpr` to a `ResolvedMethodDeclaration` and a `ClassOrInterfaceType` to a `ResolvedReferenceTypeDeclaration` — [JavaParser symbol-resolution docs](https://tessl.io/registry/tessl/maven-com-github-javaparser--javaparser-core/3.27.0/files/docs/symbol-resolution.md)
- The TypeSolver family: `ReflectionTypeSolver` (JDK or a supplied `ClassLoader`, with an `exploreJDK` flag), `JavaParserTypeSolver` (a source root directory), `JarTypeSolver` (a jar), `CombinedTypeSolver` (chains them, via constructor or `add(...)`) — [JavaParser symbol-resolution docs](https://tessl.io/registry/tessl/maven-com-github-javaparser--javaparser-core/3.27.0/files/docs/symbol-resolution.md)
- Why parsing alone is insufficient, stated plainly: "Parsing gives you the syntax tree, but a name like `foo` or a call like `list.add(x)` only gets its meaning from the declarations that live elsewhere: JDK classes, project sources, and dependency jars." Without dependencies registered, "many lookups will throw `UnsolvedSymbolException`"; ambiguous calls throw `MethodAmbiguityException`, "which lists the candidates" — [JavaParser symbol-resolution docs](https://tessl.io/registry/tessl/maven-com-github-javaparser--javaparser-core/3.27.0/files/docs/symbol-resolution.md)
- `javalang` is described by its own distribution as a "Pure Python Java parser and tools" and is vendored in Chromium's `third_party` — [PyPI javalang 0.9.0](https://pypi.python.org/pypi/javalang/0.9.0); [Chromium third_party/javalang README](https://chromium.googlesource.com/chromium/src/+/77.0.3865.75/third_party/javalang/README.chromium)
- `javalang` versions through 0.13.0 exist on PyPI — [PyPI javalang 0.12.0](https://pypi.org/project/javalang/0.12.0); [libraries.io javalang](https://libraries.io/pypi/javalang)
- Other Python-side options surfaced: `plyj` (a Java parser in Python) — [PyPI plyj](https://pypi.org/project/plyj) — and `javac-parser`, which "Exposes the OpenJDK Java parser and scanner to Python" — [PyPI javac-parser](https://pypi.org/project/javac-parser/0.1.5). `javac-parser` is a Python wrapper over the real `javac` front end, so it inherits full language coverage at the cost of a JVM dependency.
- A `tree-sitter-java` Python wheel is published and built for multiple platforms — [piwheels: tree-sitter-java](https://www.piwheels.org/project/tree-sitter-java/) — and `tree-sitter-languages` bundles many grammars including Java in one Python package — [PyPI tree-sitter-languages](https://pypi.org/pypi/tree-sitter-languages/1.10.0)
- Tree-sitter has official Java *bindings* too (`io.github.treesitter.jtreesitter`), confirming the grammar is maintained under the tree-sitter org — [tree-sitter java-tree-sitter javadoc](https://tree-sitter.github.io/java-tree-sitter/io/github/treesitter/jtreesitter/package-summary.html); [tree-sitter/java-tree-sitter](https://awesome.ecosyste.ms/projects/github.com%2Ftree-sitter%2Fjava-tree-sitter)
- GumTree's `tree-sitter-parser` demonstrates tree-sitter being used for cross-language source analysis pipelines — [GumTreeDiff/tree-sitter-parser](https://github.com/GumTreeDiff/tree-sitter-parser)

### Inferences
- **Recommended architecture for this pipeline**, two tiers:
  - *Tier 1 (do this):* `pip install tree_sitter tree_sitter_java`, parse each `.java` file to a CST, and query named nodes. Everything the extractor currently gets by regex becomes a node query: `class_declaration`, `interface_declaration`, `record_declaration`, `enum_declaration`, `annotation_type_declaration`, `method_declaration`, `constructor_declaration`, `field_declaration`, `modifiers` (which contains both access keywords and `annotation`/`marker_annotation` children), `type_parameters`, `formal_parameters`, `block`, `block_comment` (with `/**` detectable on its text), `import_declaration`, `package_declaration`. Line ranges come from node start/end points — no brace matching, no string-literal problem, no generics problem, no overload collision. This removes 12 of the 14 breakages listed above in one change, and tree-sitter's error recovery means a file using syntax newer than the grammar yields a partial tree rather than a crash.
  - *Tier 2 (only for the DI graph, if accuracy demands it):* a JVM sidecar. JavaParser + `CombinedTypeSolver(ReflectionTypeSolver, JavaParserTypeSolver(src/main/java), JarTypeSolver(each dependency jar))` emitting JSON over stdout, called once per project. This is the only way to resolve an injected interface to its implementation *correctly* across modules and jars, and to resolve `List<OrderDto>` to the actual `OrderDto` type. Cost: a JVM, a Maven/Gradle dependency resolution step to get the jars, and `UnsolvedSymbolException` handling for anything not on the classpath.
  - A project-local heuristic resolver (the bean index in the DI section) sits between the two tiers and gets most Spring projects right without a JVM, because Spring projects conventionally have one implementation per service interface *inside the project*.
- Tool-by-tool suitability: **tree-sitter-java** — syntax only, no types, Python-native, fast, error-tolerant: best fit. **JavaParser** — full AST + optional symbol solving, excellent docs, JVM. **Eclipse JDT** (`ASTParser`/`CompilationUnit`) — the most complete and most accurate binding resolution, used by Eclipse itself, heavyweight and JVM. **Spoon** — JVM, designed for analysis *and* transformation with a fully-resolved model; overkill for read-only extraction. **ANTLR Java grammar** — a grammar, not a tool; you would build the analyzer yourself, and the Python ANTLR runtime makes it Python-usable but slow and resolution-free; no advantage over tree-sitter. **javalang** — pure Python, zero native deps, but its vintage means records, sealed types, text blocks, `var`, switch expressions and modern annotations are likely unsupported; acceptable only for legacy Java 8 corpora. **javac-parser** — real `javac` coverage from Python, but still needs a JVM, and is a thin scanner/parser exposure rather than a query-friendly model.
- Pragmatic note for this project: because the pipeline already supports two languages by regex, adding Java by regex is the path of least resistance and the path of maximum silent error. Java is the stack where the cost/benefit of switching to tree-sitter flips decisively, and tree-sitter would also let the TS and Go extractors be rewritten on the same substrate later.

- **Unverified version/date facts.** PyPI pages for `javalang` and `tree-sitter-java` were blocked (PROVENANCE_REQUIRED), so I cannot cite `javalang`'s latest release date, its stated Java version ceiling, or `tree-sitter-java`'s current version. ## What narrative ordering makes a Spring Boot codebase comprehensible?

### Takeaway
Two orderings work and they are not the same: a **top-down architectural tour** (entry → config → controllers → services → repositories → entities) for orientation, and a **request trace** (one HTTP request walked through all five layers) for comprehension. The best structure for a video is the first as an overview, then the second repeated per feature, because the request trace is the only narrative that makes the DI indirection visible.

### Cited Findings
- The structural case for starting at the entry point: "The `@SpringBootApplication` annotation… implicitly defines a base 'search package'" and locating the main class in a root package "allows component scan to apply only on your project" — the entry class literally defines the boundary of everything else the video will cover — [Spring Boot, Structuring Your Code](https://docs.spring.io/spring-boot/3.5.0/reference/using/structuring-your-code.html)
- The reference's recommended layout groups a feature's four files together (`customer/{Customer, CustomerController, CustomerService, CustomerRepository}`), which is the file-level shape of a request trace — [Spring Boot, Structuring Your Code](https://docs.spring.io/spring-boot/3.5.0/reference/using/structuring-your-code.html)
- The stereotypes themselves name the layers — "the persistence, service, and presentation layers, respectively" — giving an off-the-shelf narration vocabulary — [Spring Framework, Classpath Scanning](https://docs.spring.io/spring-framework/reference/7.1/core/beans/classpath-scanning.html)
- The controller is the natural first stop because its mapping is self-describing: `@RequestMapping("/persons")` + `@GetMapping("/{id}")` + `@PathVariable Long id` + `@RequestBody Person person` fully specify the request contract without reading any body — [Spring Framework, Mapping Requests](https://docs.spring.io/spring-framework/reference/7.0/web/webflux/controller/ann-requestmapping.html)
- The repository is the natural last stop because its method names *are* the queries (`findByEmailAddressAndLastname`, `findByLastnameOrderByFirstnameAsc`) and the implementation is a generated proxy, so there is nothing deeper to descend into — [Spring Data JPA Reference 3.1.12](https://docs.spring.io/spring-data/jpa/docs/3.1.12/reference/html/)

### Inferences
- **Recommended video outline:**
  1. **Shape of the app** (1 chunk): project type, build tool, entry class, root package, the scan boundary, and the file-count-by-role table. Say out loud that Spring wires classes together at runtime by type — set the viewer's expectation before any code appears, or the rest of the video is confusing.
  2. **The route table** (1 chunk): every endpoint with verb, *fully concatenated* path, path variables, request body type, response type. This is the app's external contract and the best possible orientation frame.
  3. **The data model** (1–2 chunks): entities, their fields, and their relationships; then DTOs/records and how they differ from entities. Do this before the services, because every later method signature refers to these types.
  4. **Configuration** (1 chunk): `application.yml` keys that matter, `@Configuration`/`@Bean` definitions, profiles. Short but it explains where the "magic" values come from.
  5. **Per feature, a request trace** (3–5 chunks each): controller handler → the service *interface* it depends on → the resolved implementation (naming it explicitly, and saying how it was resolved) → the repository method → the entity/table. Repeat for each feature slice. This is where the DI graph work pays off; it is also where a wrong graph is most visible.
  6. **Cross-cutting concerns** (1–2 chunks): `@ControllerAdvice`/`@ExceptionHandler`, security config, `@Transactional` boundaries, `@Scheduled`/listeners — framed as "invoked by the container, not called from the code you have seen".
- Entry-first is right for Spring specifically (unlike, say, a React app where the component tree is the spine) because the entry class defines the component-scan boundary, and because Spring's entry file is short and annotation-dense — a perfect 60-second opening that introduces the annotation-as-architecture idea the viewer needs.
- Controllers-before-services-before-repositories follows the direction of the request and the direction of dependency, so each chunk only references types already introduced. The one exception is the data model, which must come earlier than its dependency order suggests, because it is referenced by every layer.
- The narration must explicitly verbalize the indirection at each service hop — "the controller depends on `OrderService`, an interface; the only implementation in this project is `OrderServiceImpl`, and Spring injects it at startup" — because this is the fact a viewer reading the controller source cannot see. If the pipeline's confidence on that resolution is below threshold, the script should say "one of two implementations" rather than assert.
- Visual cue opportunities specific to Spring, usable as `VISUAL[...]` tokens: highlighting the class-level `@RequestMapping` and the method-level `@GetMapping` and animating their concatenation into the full path; drawing the injected-interface → implementation arrow as a dashed "resolved at runtime" edge distinct from solid call edges; overlaying an entity's fields onto a table diagram; showing a derived query method name decomposing into its SQL.

### Gaps
- No published source found on narrative ordering for automated code explanation specifically; this section is reasoning from the cited structural facts plus the layered vocabulary Spring itself uses. The report writer should present it as a recommendation, not a documented practice.
