# Express.js / Node.js backend analysis for narrated code-explanation video generation

Scope note: findings below are drawn from Express's own routing / middleware / error-handling guides, Node's packages documentation, Mongoose and Sequelize docs, and from two concrete attempts at static Express route extraction (a tree-sitter article and `express-list-endpoints`). Where I describe an extraction *algorithm* (notably cross-file prefix resolution) the mechanics are my own engineering inference built on the cited syntax facts, and are labelled as such under **Inferences**.

Blocked sources (permission/provenance or rate limit, could not be read): `https://nodejs.org/api/esm.html`, `https://mongoosejs.com/docs/guide.html`, `https://www.typescriptlang.org/docs/handbook/jsdoc-supported-types.html`, `https://swagger-autogen.github.io` (only the GitHub landing page was readable). Substitutes were used where possible and are cited as such.

## How are Express routes declared, in all the common forms a tool must recognize — and how is a route's FULL path resolved when a router is mounted under a prefix in another file?

### Takeaway
Express offers at least seven syntactically distinct ways to register a route, and the *path string at the call site is only a suffix* — the full URL is the concatenation of every mount prefix on the chain of `app.use(prefix, router)` / `router.use(prefix, subRouter)` calls, which almost always live in different files from the route itself. Any single-file regex pass therefore reports paths that are wrong (too short) for the majority of real Express projects, and silently mislabels non-route calls as routes.

### Cited Findings
- **`app.METHOD(path, handler)`**: "Routes are defined with methods on the `app` object that match HTTP methods" and "Express supports methods that correspond to all HTTP request methods: `get`, `post`, and so on." Example: `app.get('/', (req, res) => { res.send('GET request to the homepage'); });` — [Express routing guide](https://expressjs.com/en/guide/routing.html)
- **`app.all(path, fn)`** is "a special routing method, used to load middleware functions at a path for *all* HTTP request methods." Example: `app.all('/secret', (req, res, next) => {...})` — [Express routing guide](https://expressjs.com/en/guide/routing.html)
- **Chained `app.route(path).get().post().put()`**: "You can create chainable route handlers for a route path by using `app.route()`. Because the path is specified in a single location, this helps to create modular routes and reduces redundancy and typos."
  ```js
  app
    .route('/book')
    .get((req, res) => { res.send('Get a random book'); })
    .post((req, res) => { res.send('Add a book'); })
    .put((req, res) => { res.send('Update the book'); });
  ```
  — [Express routing guide](https://expressjs.com/en/guide/routing.html)
- **`express.Router()` in a separate file**: "Use the `express.Router` class to create modular, mountable route handlers. A `Router` instance is a complete middleware and routing system; for this reason, it is often referred to as a 'mini-app'." The documented example file defines `router.get('/')` and `router.get('/about')` and ends with `export default router;` — [Express routing guide](https://expressjs.com/en/guide/routing.html)
- **Mounting under a prefix, in the parent file**: `const birds = require('./birds'); ... app.use('/birds', birds);` — and "The app will now be able to handle requests to `/birds` and `/birds/about`, as well as call the `timeLog` middleware function that is specific to the router." This is the canonical two-file split: the route file says `'/about'`, the real URL is `/birds/about`. — [Express routing guide](https://expressjs.com/en/guide/routing.html)
- **`Router({ mergeParams: true })`**: "If the parent route `/birds` has path parameters, it will not be accessible by default from the sub-routes. To make it accessible, you will need to pass the `mergeParams` option to the Router constructor." — [Express routing guide](https://expressjs.com/en/guide/routing.html)
- **Route params, wildcards, optional segments (Express 5 / path-to-regexp v8 syntax)**: named `'/users/:userId/books/:bookId'`; wildcard `'/files/*filepath'` (captured as an array, `req.params.filepath` → `[ 'images', 'logo.png' ]`); braces for optional segments — `'/{*splat}'`, `'/:file{.:ext}'`, `'/user/{:id}'`, `'/order{/:id}'`. Express 5 also warns: "Regexp characters are not supported inside string paths, so a parameter cannot be restricted with a suffix such as `:userId(\d+)`. Use an array of paths or a full regular expression instead." — [Express routing guide](https://expressjs.com/en/guide/routing.html)
- **Regex paths**: `app.get(/a/, ...)` and `app.get(/.*fly$/, ...)` are valid route declarations — i.e. the first argument is not always a string literal. — [Express routing guide](https://expressjs.com/en/guide/routing.html)
- **Handler arrays and multiple callbacks**: `app.get('/example/c', [cb0, cb1, cb2]);` and mixed forms `app.get('/example/d', [cb0, cb1], fn, fn)` are documented; "each callback except the last must call `next()`." — [Express routing guide](https://expressjs.com/en/guide/routing.html)
- **`next('route')` creates duplicate declarations of the same path** that are both real: `app.get('/user/:id', ...)` declared twice, the first calling `next('route')` for `id === '0'`, the second being the "Special handler for user ID 0". — [Express routing guide](https://expressjs.com/en/guide/routing.html)
- **`app.use(path, router, fallback)`** is legal — a router and a plain handler mounted at the same prefix: `app.use('/admin', router, (req, res) => { res.sendStatus(401); });` — [Express middleware guide](https://expressjs.com/en/guide/using-middleware.html)
- **Runtime introspection is what existing tooling actually relies on.** `express-list-endpoints` "takes your app or router instance" and its README warns: "Pay attention that before call this script the router or app must have the endpoints registered due to detect them." It returns objects with `path`, `methods`, `middlewares`, shows unnamed handlers as `anonymous`, "omits 'all' handlers", and "only works for express 4.* versions. It's not compatible with express 5 yet." It requires an app/router *instance*, not source files. — [express-list-endpoints README](https://github.com/AlbertoFdzM/express-list-endpoints)
- **A naive AST/tree-sitter matcher over-matches and under-captures.** A published tree-sitter-javascript example uses the query
  ```
  (call_expression
    function: (member_expression
      object: (identifier) @router.obj
      property: (property_identifier) @http.method)
    arguments: (arguments
      (string) @route.path
      (_)* @middleware.name))
  ```
  which "never names `get`, `post`, or `use`" — it matches *any* `object.property("string", ...)` call. In the author's own sample output this makes `res.send('User list')` appear as a route (`SEND 'User list' (res)`), and a route declared as `router.post('/api/login', logRequestMiddleware, handler)` reports "No Middleware" because the identifier argument is not captured. — [Getting started with tree-sitter: Express API parsing](https://dev.to/lovestaco/getting-started-with-tree-sitter-syntax-trees-and-express-api-parsing-5c2d)
- **`swagger-autogen` claims source-level detection but its public landing page does not document the mechanism**: "It can identify the endpoints and automatically capture methods such as get, post, put, and so on. It also identifies paths, routes, middlewares, response status codes, parameters in the path, header, query and body." It gives no statement on how routers in separate files or `app.use('/prefix', router)` prefixes are resolved, deferring to its docs site; issues are disabled on the repo. — [swagger-autogen README](https://github.com/davibaltar/swagger-autogen)

### Inferences
- **The full-path resolution problem, stated precisely.** A route's effective URL is `join(mountPrefix₁, mountPrefix₂, …, localPath)`. To compute it statically a tool needs four linked facts, three of which are *not* in the file containing the route:
  1. In the route file: which local identifier is the Router (`const router = express.Router()`), and what that file exports (`module.exports = router` / `export default router`).
  2. In the parent file: which `require()`/`import` specifier binds to that file, and under which local name (`const birds = require('./birds')` → `birds`).
  3. In the parent file: the `app.use('/birds', birds)` call that associates a prefix string with that local name.
  4. Transitively: the parent may itself be a router mounted under another prefix (`app.use('/api/v1', apiRouter)` → `apiRouter.use('/birds', birdsRouter)` → `/api/v1/birds/about`).
  A workable pipeline is therefore two-pass and project-wide, not per-file: **pass 1** builds a per-file symbol table — module path, module system, exported binding(s), identifiers known to hold a Router, and all local `METHOD(path, …)` registrations with line ranges; **pass 2** builds a mount graph whose edges are `(parentFile, prefixString) → resolvedChildFile` derived from `app.use`/`router.use` calls whose non-first argument resolves, through the file's import table, to another analysed file; then a DFS from each `express()` app instance accumulates prefixes and emits full paths. Node resolution rules (extensionless `require('./birds')` → `birds.js`, `birds/index.js`, `.mjs`, `.cjs`) must be reimplemented for edge resolution.
- **Cases where even this is undecidable statically, and where the honest output is "assumed/unknown" rather than a guess**: prefixes built from variables or template literals (`app.use(`${BASE}/users`, usersRouter)`), prefixes from config objects, dynamic registration in a loop (`routes.forEach(r => app[r.method](r.path, r.handler))`), auto-loaders that `fs.readdirSync('./routes')` and mount each file by filename, regex route paths, and arrays of paths. For a narration pipeline the right behaviour is to emit the local path plus `assumed: true` and a note naming the unresolved expression, never a fabricated full path.
- **What a regex-only, TypeScript-tuned pipeline silently gets wrong on plain-JS Express** (each item follows directly from a cited fact above):
  - Reports `/about` instead of `/birds/about` — the single most common and most damaging error, because the narration then names a URL that does not exist in the running app.
  - Misses chained `app.route('/book').get(...).post(...)` entirely if the regex expects `app.get(` with a string literal immediately after the method name; the method verbs are on a *continuation* of the expression and the path is attached to `.route(`.
  - Misses `app.all`, and misses the second of two `next('route')` declarations of the same path (or reports a bogus duplicate without explaining the fall-through).
  - Treats `app.use('/users', handler)` (a path-mounted middleware) as a route, and treats `app.use(express.json())` as something it cannot classify.
  - Mislabels non-route member calls that happen to take a string first argument — the tree-sitter article's own output shows `res.send('User list')` surfacing as an endpoint, and a regex is strictly weaker than that query.
  - Mishandles Express 5 brace syntax (`/order{/:id}`, `/{*splat}`) and `*name` wildcards when its parameter regex was written for `:param` only; and breaks outright on regex-literal route paths.
  - Loses the handler chain: the middleware arguments between the path and the final handler are exactly what makes an endpoint's behaviour explainable (auth, validation), and they are identifiers, not strings.
  - Matches route-shaped strings inside comments and inside template strings/docs, because regex has no notion of a comment or a string context.

### Gaps
- No primary documentation states Express's exact prefix-stripping semantics for `app.use(path, …)` (how `req.url` is rewritten and `req.baseUrl` set); the middleware guide explicitly stops short — "The page does not explain path-matching or prefix-stripping rules for `app.use(path, ...)` in depth. Those details are in the linked API reference" — and I did not fetch the API reference. Worth confirming from `https://expressjs.com/en/5x/api.html` before implementing trailing-slash/`baseUrl` joining rules.
- I could not verify how `swagger-autogen` actually resolves cross-file prefixes (docs site not read). Treat it as an existence proof that source-level detection is attempted, not as a design to copy.
- I found no maintained, widely-used library that does *static*, source-only, cross-file Express route extraction with resolved prefixes. `express-list-endpoints` is runtime-only and Express 4-only. This appears to be a genuinely unsolved-in-the-ecosystem problem rather than something to delegate to a dependency.

## Middleware: declaration, ordering, identification by signature, and error middleware

### Takeaway
Middleware is identified by arity and position, not by name: three parameters `(req, res, next)` is ordinary middleware, four parameters `(err, req, res, next)` is an error handler and Express will not treat it as one otherwise. Because the stack is executed strictly in registration order and any handler may end the cycle, *order is semantics* — an explanation that lists middleware without its order is not an explanation of the request lifecycle.

### Cited Findings
- Middleware functions receive `req`, `res`, and "the next middleware function in the application's request-response cycle, commonly named `next`", and may "execute any code, modify the request and response objects, end the request-response cycle, pass control to the next middleware function." "If a middleware function does not end the request-response cycle, it must call `next()` … Otherwise, the request will be left hanging." — [Express middleware guide](https://expressjs.com/en/guide/using-middleware.html)
- **Application-level**: "Bind application-level middleware to an instance of the app object by using the `app.use()` and `app.METHOD()` functions". Mountable on a path: `app.use('/user/:id', (req, res, next) => {...})`. Several functions at one mount point form "a middleware sub-stack". Arrays of middleware are reusable: `const logStuff = [logOriginalUrl, logMethod]; app.get('/user/:id', logStuff, handler);` — [Express middleware guide](https://expressjs.com/en/guide/using-middleware.html)
- **Router-level**: "Router-level middleware works the same way as application-level middleware, except it is bound to an instance of `express.Router()`", loaded via `router.use()` / `router.METHOD()`. A `router.use(fn)` with no path "is executed for every request to the router". — [Express middleware guide](https://expressjs.com/en/guide/using-middleware.html)
- **Error middleware is identified purely by four-argument arity**: "Error-handling middleware always takes *four* arguments. You must provide four arguments to identify it as an error-handling middleware function. Even if you don't need to use the `next` object, you must specify it to maintain the signature. Otherwise, the `next` object will be interpreted as regular middleware and will fail to handle errors." — [Express middleware guide](https://expressjs.com/en/guide/using-middleware.html)
- **Error middleware must come last**: "You define error-handling middleware last, after other `app.use()` and routes calls." Multiple error handlers can be chained (`app.use(logErrors); app.use(clientErrorHandler); app.use(errorHandler);`), each forwarding with `next(err)`. — [Express error-handling guide](https://expressjs.com/en/guide/error-handling.html)
- **Order is observable behaviour**: "The second route will not cause any problems, but it will never get called because the first route ends the request-response cycle." — [Express middleware guide](https://expressjs.com/en/guide/using-middleware.html)
- **Error mode short-circuits the normal stack**: "If you pass anything to the `next()` function (except the string `'route'`), Express regards the current request as being an error and will skip any remaining non-error handling routing and middleware functions." And "`next(err)` will skip all remaining handlers in the chain except for those that are set up to handle errors." — [Express error-handling guide](https://expressjs.com/en/guide/error-handling.html)
- **`next('route')` vs `next('router')`**: `next('route')` skips the rest of the current route's stack and works "only in functions loaded with `app.METHOD()` or `router.METHOD()`"; `next('router')` "exits the router instance and passes control back out" — demonstrated by a router that 401s via a fallback handler at its mount point. — [Express middleware guide](https://expressjs.com/en/guide/using-middleware.html)
- **Built-ins a tool should recognize by name**: `express.static`, `express.json`, `express.raw`, `express.text`, `express.urlencoded`; third-party middleware is loaded as `app.use(cookieParser())` after `require('cookie-parser')`. — [Express middleware guide](https://expressjs.com/en/guide/using-middleware.html)
- **A default error handler always exists at the end**: "Express comes with a built-in error handler … This default error-handling middleware function is added at the end of the middleware function stack." It derives `res.statusCode` from `err.status`/`err.statusCode` (values outside 4xx/5xx become 500), sends `err.stack` outside production, and applies `err.headers`. A custom handler should delegate when `res.headersSent`. — [Express error-handling guide](https://expressjs.com/en/guide/error-handling.html)

### Inferences
- **Signature-based classification is reliable enough to be worth doing precisely, and arity is cheap to get right from an AST and easy to get wrong with regex.** The classification a tool needs per `app.use`/`router.use` argument: 4 params → error handler; 3 params → middleware; 2 params → terminal handler (the last in a chain legitimately omits `next`); a *call expression* argument (`express.json()`, `cors()`) → a middleware factory, and the thing to narrate is the factory's name and its options object, not an anonymous function. Regex cannot count parameters across a multi-line arrow function, cannot tell `(err, req, res, next)` from `(req, res, next)` when the names are `(e, q, s, n)` or minified, and cannot see that a middleware passed by identifier is defined in `middleware/auth.js`.
- **The ordered middleware chain is the single highest-value artifact for an Express explanation video**, and it is *not* one of the seven things the current pipeline extracts. The extractor should emit an ordered list per app and per router: `[{order, kind: app|router|error, mountPath|null, name, sourceFile, lineRange, isFactoryCall, options}]`. Narration then has a spine: "every request first passes through `helmet()`, then JSON body parsing, then the request logger; only requests carrying a valid token get past `requireAuth` at `/api`…".
- **Ordering must be recovered as registration order within a file, then composed along the mount graph** — i.e. the order in which `app.use` statements appear textually in the entry file, with each mounted router expanded in place at its mount point. A per-file extractor that reports middleware as an unordered set destroys the only information that makes the chain explainable.
- Because error handlers must be registered last, their *position* is a correctness fact worth narrating (and worth flagging when violated: an error handler registered before routes will never fire).

### Gaps
- Express does not document any mechanism for declaring middleware order declaratively, so there is no metadata source — order is only recoverable from statement position in source (or from runtime introspection). I found no documentation suggesting otherwise.

## How are controllers / services / models organized? Is there a dominant convention?

### Takeaway
There is no convention. Unlike Django (apps with `models.py`/`views.py`), Spring (annotated stereotypes) or Angular (CLI-enforced layout), Express prescribes nothing beyond "a Router is a mini-app", and published Express projects disagree with each other on layout. A narration tool must therefore *discover* the architecture per project rather than assume it.

### Cited Findings
- Node has "few (if any) true conventions," which the author names as one of its most painful aspects; "I don't believe there is one best project structure for Express projects"; and of the Express REST API structures findable online, "you'll find very few of them follow the same organization." — [Project structure for an Express REST API when there is no standard way](https://dev.to/ccleary00/project-structure-for-an-express-rest-api-when-there-is-no-standard-way-4gk3)
- The two competing families are "more traditional MVC (or MVC-ish)" folders by technical role versus "the cool new kid, components" — "You can simply group the routes, controllers, services, etc. into a component folder." Neither is presented as correct. — [same source](https://dev.to/ccleary00/project-structure-for-an-express-rest-api-when-there-is-no-standard-way-4gk3)
- Express's own routing guide frames the only official structural unit as the mountable Router "mini-app", recommending `express.Router` "to create modular, mountable route handlers" — it says nothing about controllers, services or models. — [Express routing guide](https://expressjs.com/en/guide/routing.html)

### Inferences
- **The mount graph, not the folder tree, is the architecture.** Since folders are unreliable, the tool should derive structure from code relationships: app entry → middleware chain → mounted routers (by prefix) → handler functions → the modules those handlers import (controllers/services) → the modules those import (models/DB). This graph exists in every Express project regardless of whether it calls its folders `controllers/` or `features/`.
- **Folder names are a weak secondary signal, usable for labelling but not for structure**: directory names matching `routes?|controllers?|services?|models?|middlewares?|repositor(y|ies)|utils?|config` on one hand, versus a flat set of sibling feature directories each containing route+controller+model files on the other. A reasonable classifier: if ≥2 of the role-named directories exist at one level → narrate as layered/MVC-ish; if sibling directories each contain a route-registering file → narrate as feature/vertical-slice; otherwise narrate as "ad hoc" and fall back to the mount graph. This heuristic is mine, not documented anywhere.
- **Controllers are usually only recognizable by reference, not by shape.** `router.get('/:id', userController.getUser)` and `router.post('/', requireAuth, validate(schema), createUser)` are the common shapes; a plain-JS "controller" is just an exported function with `(req, res)` or `(req, res, next)` parameters. So the useful extraction is the *edge*: route → handler identifier → the module it was imported from → the function definition's line range in that module. That cross-file handler resolution is the same import-table machinery needed for mount-prefix resolution, so it comes almost free once that is built.
- Practical consequence for the video pipeline: do not promise a fixed chapter list derived from folder names. Chapter the video off the mount graph and label chapters with whatever names the project actually uses.

### Gaps
- I found no quantitative survey of Express project layouts (e.g. what fraction use `controllers/`), so the "no dominant convention" claim rests on practitioner testimony plus the absence of any structural prescription in official docs, not on measured data. Several blog posts proposing "best" structures exist (e.g. [oneuptime](https://oneuptime.com/blog/post/2026-02-02-express-project-structure/markdown), [dev.to guides](https://dev.to/moibra/best-practices-for-structuring-an-expressjs-project-148i)) but they are opinion pieces and they disagree, which is itself the finding.

## CommonJS vs ESM: require() vs import, and determining what is "exported"

### Takeaway
A `.js` file's module system is not determined by its contents but by the nearest `package.json`'s `type` field, so a dependency extractor cannot decide how to read a file from the file alone — it must read project metadata first. In practice a plain-JS Express analyser must support both syntaxes simultaneously, including the hybrid files that `require()` some things and `export` others.

### Cited Findings
- **ES modules** are: `.mjs` files, `.js` files whose package.json has `"type": "module"`, string input with `--input-type=module`, and files containing ES module syntax. **CommonJS** is: `.cjs` files, `.js` files with `"type": "commonjs"`, `.js` files with no package.json or no `type` field, and `--input-type=commonjs`. "`.mjs` is always ES module and `.cjs` is always CommonJS. A `.js` file follows the package's `"type"` field." — [Node packages documentation (mirror of nodejs.org/api/packages)](https://www.mintlify.com/nodejs/node/api/packages); the canonical page `https://nodejs.org/api/esm.html` was blocked for me, so this is a mirror, not the primary.
- Dual packages are expressed through an `exports` map with `"import"` and `"require"` conditions plus a `"main"` fallback; the `"import"` condition covers `import`/`import()` and `"require"` covers `require()`. — [same source](https://www.mintlify.com/nodejs/node/api/packages)
- Express's own documentation ships its samples "in CommonJS, ESM, and TypeScript variants" — the routing guide's router example ends in `export default router;` while the mounting example uses `const birds = require('./birds');`, i.e. the official docs mix both forms. — [Express routing guide](https://expressjs.com/en/guide/routing.html) / [Express middleware guide](https://expressjs.com/en/guide/using-middleware.html)

### Inferences
- **Import/dependency extraction must handle, at minimum, these shapes:** `require('x')` bare; `const x = require('x')`; `const { a, b } = require('x')`; `const x = require('x').default`; `require('./x')(app)` (immediately-invoked module, common in auto-loaders and in `module.exports = (app) => {…}` route files); conditional/lazy `require` inside a function body; `import x from 'x'`; `import { a as b } from 'x'`; `import * as ns from 'x'`; bare `import 'x'` (side-effect only, e.g. `import './db'`); `export … from` re-exports; and dynamic `await import('x')`. Only the first and the seventh are what a simple regex usually catches.
- **"Exported" is determined differently in each system, and the distinction matters for mount resolution because the thing exported is usually the Router:**
  - CommonJS, whole-module export: `module.exports = router` → the module's single export *is* the Router; the parent's `const r = require('./f')` binds it directly, so `app.use('/x', r)` mounts that file's routes.
  - CommonJS, named: `module.exports.foo = fn`, `exports.foo = fn`, or `module.exports = { foo, bar }` → named exports; `const { foo } = require('./f')` binds one. Note `exports.foo = …` and `module.exports.foo = …` are equivalent only while `module.exports` has not been reassigned — a file that does `module.exports = router` and then `exports.helper = …` has effectively dropped `helper`, a real bug class a tool should not silently normalise away.
  - CommonJS, conditional/mutated exports (`if (isProd) module.exports = a; else module.exports = b;`) → statically ambiguous.
  - ESM: `export default router` → default export; `export const foo = …` / `export function foo(){}` / `export { foo, bar as baz }` → named; `export * from './x'` → re-export, which means resolving the *next* file to know the names.
  - Interop: `import r from './f'` where `f` is CJS binds `module.exports`, so a `module.exports = router` file imports cleanly as a default — this is why mixed-system projects still mount correctly and why the resolver must treat "CJS whole-module export" and "ESM default export" as the same node type in its symbol table.
- **Recommended symbol-table shape** (feeds both the mount graph and the handler-resolution graph): per file, record `{absPath, moduleSystem: 'cjs'|'esm'|'mixed', imports: [{localName|destructured, specifier, resolvedPath, kind}], exports: [{exportedName|'default'|'module', localBinding, isRouterInstance, lineRange}]}`. Determining `moduleSystem` requires walking up to the nearest `package.json` and reading `type`, with `.mjs`/`.cjs` overriding — a project-level prerequisite step the current per-file pipeline presumably does not have.
- A parser must be configured for *both* source types, since an AST parser in strict CJS script mode will throw on `import`/`export` and in strict module mode will reject things like `with` or top-level `await`-free assumptions. Babel's `sourceType: 'unambiguous'` and tree-sitter-javascript (which parses both) both sidestep this; a regex pass has no such failure mode but also no such understanding.

### Gaps
- I could not read the primary `nodejs.org/api/esm.html` page, so I have no citable statement on **named-export detection from CommonJS via `cjs-module-lexer`** or on **`require(esm)`** support (unflagged in recent Node). Both are relevant if the pipeline ever needs to know which named exports an ESM importer can legally pull from a CJS file; flag as unverified.

## Plain JavaScript has no type annotations — what is lost, and what can be read back?

### Takeaway
Losing TypeScript costs the analyser exactly the things that make an API explanation concrete: request/response body shapes, params, DTOs, and entity fields. Almost all of it is recoverable, because real Express projects re-declare those shapes at runtime — in Mongoose/Sequelize models and in Zod/Joi validation schemas — and those are ordinary object literals a parser can read far more reliably than it could read a TS interface.

### Cited Findings
- **JSDoc is a real, type-checkable annotation channel in plain `.js`.** `/** @type {string} */ let myString;` is the documented equivalent of `let myString: string;`, and parameter forms include required, `=`-optional, bracket-optional and defaulted: `@param {string} p1`, `@param {string=} p2`, `@param {string} [p3]`, `@param {string} [p4="test"]`, with `@return {string}`. TypeScript's support for checking JS "arrived with the `--checkJs` compiler option in TypeScript 2.3." Caveats from the same source: "not all TypeScript syntax is supported in JSDoc", tooling support is weaker than for TS proper, and annotations live in comments, which makes code "harder to follow." — [TypeScript vs. JSDoc JavaScript for static type checking (LogRocket)](https://dev.to/logrocket/typescript-vs-jsdoc-javascript-for-static-type-checking-18i4). Note: the primary TS handbook page listing supported JSDoc tags was blocked for me, so the exact supported-tag list (`@typedef`, `@callback`, `@template`, `@satisfies`, `@import`) is **unverified** here; only `@type`, `@param`, `@return` and the `@typedef { import(...) }` form (shown in a reader comment on that page) are cited.
- **Mongoose models are directly readable data models.** A schema is a plain object literal of field → type: `const schema = new mongoose.Schema({ name: String, size: String }); const Tank = mongoose.model('Tank', schema);` — [Mongoose models docs via Context7](https://github.com/automattic/mongoose/blob/master/docs/models.md). Constraints appear as nested option objects: `new Schema({ name: { type: String, required: true } })` — [Mongoose documents docs](https://github.com/automattic/mongoose/blob/master/docs/documents.md). Relations are explicit and machine-readable via `ref`:
  ```js
  const personSchema = Schema({
    _id: Schema.Types.ObjectId,
    name: String,
    age: Number,
    stories: [{ type: Schema.Types.ObjectId, ref: 'Story' }]
  });
  const storySchema = Schema({
    author: { type: Schema.Types.ObjectId, ref: 'Person' },
    title: String,
    fans: [{ type: Schema.Types.ObjectId, ref: 'Person' }]
  });
  ```
  — [Mongoose populate docs](https://github.com/automattic/mongoose/blob/master/docs/populate.md). (`mongoosejs.com/docs/guide.html` itself was blocked; these are the repo docs sources Context7 returned.)
- **Sequelize models and their associations are equally readable.** Models are declared with `sequelize.define('Name', { field: DataTypes.X })` — e.g. `const UserProjects = sequelize.define('UserProjects', { started: DataTypes.BOOLEAN })` — and relations are explicit static calls: `Profile.hasMany(User)`, `Profile.belongsTo(User)`, `User.hasOne(Profile)`, `User.belongsToMany(Project, { through: 'UserProjects' })`, with documented semantics ("Defines a 1:n association between two models. The foreign key is added on the target model."; belongsToMany "Create an N:M association with a join table. Defining `through` is required."). Associations are also retrievable at runtime from `Model.associations`. — [Sequelize model.js source/docs via Context7](https://github.com/sequelize/sequelize/blob/main/packages/core/src/model.js), [association usage example](https://github.com/sequelize/sequelize/blob/main/packages/core/test/integration/instance/values.test.js)

### Inferences
- **What is actually lost versus TypeScript**, concretely: (a) request shapes — in TS you often find `Request<Params, ResBody, ReqBody>` or an interface for the body, in JS `req.body` is `any` and the fields are only discoverable from property reads (`const { email, password } = req.body`); (b) response shapes — `res.json({...})` object literals are the only evidence; (c) named DTO/domain types that narration can refer to by name; (d) function signatures — arity only, no parameter types or return type; (e) the arity-based middleware classification stays intact (it is positional, not typed), so middleware detection is one of the few things *not* degraded by losing TS.
- **Recovery ladder, best to worst, for a narration pipeline:**
  1. **ORM/ODM schemas — best source, read these first.** Mongoose `new Schema({…})` and Sequelize `define`/`Model.init` give field names, types, required/allowNull, and explicit relations (`ref`, `hasMany`, `belongsTo`, `through`). They are object literals, so even a regex can get field names, though nested option objects and arrays (`[{ type: …, ref: 'Story' }]`) need real bracket matching. Relations let the video draw an accurate entity diagram.
  2. **Validation schemas — best source for request shapes.** Zod (`z.object({ email: z.string().email(), age: z.number().optional() })`) and Joi (`Joi.object({ … })`) are typically attached to exactly the routes whose bodies they describe, often via a `validate(schema)` middleware at the route — so the extractor can bind a request schema to an endpoint, which is precisely the TS `ReqBody` information. Caveat: I did not fetch Zod/Joi primary docs in this pass, so treat the exact API surface as from my prior knowledge, not cited here.
  3. **JSDoc `@typedef`/`@param`/`@returns`** — genuine type information when present, but presence is sporadic and the LogRocket source's own complaints (verbosity, partial TS coverage) predict that. A tool should read it opportunistically and never depend on it.
  4. **Inference from usage** — destructuring of `req.body`/`req.params`/`req.query`, and `res.json`/`res.status().json()` literals. Lossy and should be reported with `assumed: true`.
  5. **OpenAPI/Swagger artifacts already in the repo** (a `swagger.json`, or `swagger-autogen` comments) — if present, these are an authoritative cross-check on the route list and on request/response shapes, and a cheap way to validate the mount-prefix resolver's output.
- Because all of the above are *call expressions with object-literal arguments*, the AST win over regex is large here: nested objects, arrays of objects, chained builders (`z.string().min(3).email()`) and trailing commas are exactly where regex degrades silently.

### Gaps
- Primary citations for Zod and Joi schema syntax, and for the complete TypeScript-supported JSDoc tag list, are missing (blocked/not fetched). The claims about them above should be verified before being stated as fact in the report.

## Async patterns, and what the narration should say about them

### Takeaway
Express's error-propagation behaviour differs by async style, and in Express 5 async handlers finally propagate rejections automatically — which means the once-ubiquitous `asyncHandler`/`catchAsync` wrapper is a *version-dependent* idiom. A tool that does not recognise wrappers will fail to find the real handler at all, since the handler is an argument to the wrapper, not an argument to the route.

### Cited Findings
- **Synchronous throws are free**: "Errors that occur in synchronous code inside route handlers and middleware require no extra work. If synchronous code throws an error, then Express will catch and process it." — [Express error-handling guide](https://expressjs.com/en/guide/error-handling.html)
- **Express 5 auto-handles promise rejections**: "Route handlers and middleware that return a Promise call `next(value)` automatically when they reject or throw an error, and `async` functions always return a Promise, so their errors reach Express with no extra work." If the rejection has no value, "`next` will be called with a default Error object provided by the Express router." — [Express error-handling guide](https://expressjs.com/en/guide/error-handling.html)
- **Unreturned promise chains are a real bug**: "If the promise is not returned, Express does not know it exists, and you must route the error yourself by providing `next` as the final catch handler. Without it, the rejection would be unhandled and crash the process." Correct form: `.catch(next)`. — [Express error-handling guide](https://expressjs.com/en/guide/error-handling.html)
- **Callback-style async needs explicit forwarding**: "Errors produced by callback-based APIs, such as those in `node:fs`, are not thrown and are not part of any promise. The callback receives them as its first argument, and you must pass them to the `next()` function yourself" — `fs.readFile(path, (err, data) => { if (err) { next(err) } else { res.send(data) } })`. For non-error-first async (e.g. `setTimeout`) you must `try/catch` inside the callback and call `next(err)`. "Whichever method you use, if you want Express error handlers to be called in and the application to survive, you must ensure that Express receives the error." — [Express error-handling guide](https://expressjs.com/en/guide/error-handling.html)

### Inferences
- **Wrapper recognition is a structural requirement, not a nicety.** `router.get('/:id', asyncHandler(async (req, res) => {…}))` and `catchAsync(fn)`, `wrapAsync(fn)`, `tryCatch(fn)`, `expressAsyncHandler(fn)` all place the real handler one call-expression deeper. A route extractor must unwrap single-argument call expressions whose argument is a function to find the handler's body and line range; otherwise it reports the handler as `asyncHandler` (an "anonymous"/wrong name — note `express-list-endpoints` already surfaces unnamed handlers as `anonymous`) and attaches the wrong line range to the narration, so the video highlights the wrong code.
- **What the narration should actually say**, per style detected: callbacks → "errors arrive as the first callback argument and must be forwarded with `next(err)`"; unreturned `.then` chains → flag the missing `.catch(next)` as a crash risk, citing the docs' own wording; `async`/`await` handlers → on Express 5 note that rejections reach the error middleware automatically, on Express 4 note that they do *not* and look for the wrapper; presence of a wrapper in an Express 5 project → worth narrating as legacy/defensive rather than necessary. Detecting the Express major version from `package.json` is therefore a prerequisite for saying anything true about async error flow, and is a cheap project-level read.
- A useful derived fact for explanation: "where does an error raised here end up?" is answerable once the middleware chain and the error-handler positions are known — follow the chain forward to the first 4-arity handler, falling back to Express's built-in handler, which the docs confirm is always appended at the end of the stack.

### Gaps
- `express-async-handler` / `express-async-errors` package documentation was not fetched; the wrapper names listed above come from my prior knowledge of common idioms, not from a cited source. Verify before naming specific packages in the report.

## What existing tools parse Express well, and what narrative ordering makes an Express codebase comprehensible?

### Takeaway
No existing tool solves static cross-file Express route resolution; the ecosystem splits into runtime introspectors (accurate but need the app to boot) and source scanners (no boot, but documented accuracy limits). For the pipeline, the realistic answer is a general JS parser (Babel or tree-sitter-javascript) plus a project-level resolver of your own — and the narration should follow the request's own path through the system, which is also the order in which the resolver discovers things.

### Cited Findings
- **Runtime introspection**: `express-list-endpoints` requires an app/router instance with routes already registered, returns `path`/`methods`/`middlewares`, labels unnamed handlers `anonymous`, omits `all` handlers, and supports Express 4 only — "It's not compatible with express 5 yet." — [express-list-endpoints README](https://github.com/AlbertoFdzM/express-list-endpoints)
- **Source scanning**: `swagger-autogen` claims to identify endpoints, methods, "paths, routes, middlewares, response status codes, parameters in the path, header, query and body", with extra detail supplied "using comments in code"; its repo has issues disabled and documents the mechanism only on an external site. — [swagger-autogen README](https://github.com/davibaltar/swagger-autogen)
- **General JS parsers that handle Express source**: tree-sitter-javascript via the `tree-sitter` Node binding (`parser.setLanguage(JavaScript)` then a query over the tree) is demonstrated end-to-end on Express route extraction; "The syntax trees produced by Tree-sitter allow for deeper analysis than traditional regex-based linters." The same article's output demonstrates that a loose query produces false positives (`res.send` reported as a route) and misses identifier middleware. — [Getting started with tree-sitter: Express API parsing](https://dev.to/lovestaco/getting-started-with-tree-sitter-syntax-trees-and-express-api-parsing-5c2d)
- Express's own guide names the Router "mini-app" as the unit of modularity and shows the canonical entry-file composition order — built-in/third-party middleware via `app.use(...)`, then mounted routers via `app.use('/prefix', router)`, then error handlers "last, after other `app.use()` and routes calls." — [Express middleware guide](https://expressjs.com/en/guide/using-middleware.html), [Express error-handling guide](https://expressjs.com/en/guide/error-handling.html)

### Inferences
- **Tool recommendation for a regex-based pipeline adding Express support.** The honest conclusion from the above is that Express cannot be done accurately with per-file regex, because the central fact (full route path) is cross-file. Options, in order of cost/benefit for this pipeline: (1) **tree-sitter-javascript** — one grammar handles `.js/.mjs/.cjs` and JSX, has Python bindings (so it fits a Python pipeline without a Node sidecar), is error-tolerant on partial/odd files, and gives exact byte/line ranges, which the video pipeline already needs for highlight cues; its weakness is no scope/binding resolution, which you must build anyway for the mount graph. (2) **@babel/parser** (with Acorn/Espree as lighter alternatives; Espree is ESLint's parser, Acorn its base) — richest JS/JSX/Flow/TS coverage and `sourceType: 'unambiguous'`, but requires running Node from the pipeline. (3) **Runtime introspection as a verification oracle only**, not as the primary extractor: booting an arbitrary repo is unsafe and unreliable for a video generator, and `express-list-endpoints` is Express-4-only.
- **A hybrid is the pragmatic answer**: keep regex for cheap per-file signals (leading doc comments, obvious `require`/`import` lines, function line ranges) and add a real parser for the four things regex provably cannot do — route path resolution across files, middleware arity/order, handler-identifier resolution to a definition, and object-literal schema extraction. Emit confidence per fact and mark anything that depended on an unresolved expression as `assumed`.
- **Narrative ordering for the video** — follow the request, because that is the only ordering intrinsic to Express rather than imposed by folder layout:
  1. **Project frame** (30–45s): module system (`type` field), Express major version, ORM/validation libraries present, how the app is started. These facts are prerequisites for everything said later and are cheap to state.
  2. **Entry point** (`server.js`/`app.js`/`index.js`): app creation, config/env, DB connection, `app.listen` — the "boot".
  3. **The global middleware chain, in registration order**, named one by one with what each does to the request. This is the spine of the explanation and the thing a regex pipeline currently omits entirely.
  4. **The mount map**: each `app.use('/prefix', router)` as a branch, giving the viewer the full URL namespace before any individual endpoint is shown. Show this as a tree/diagram — it is the moment the cross-file resolution pays off visually.
  5. **Per-router chapters**: router-level middleware first, then endpoints in declaration order, each narrated as *full resolved path* → middleware chain → handler, with the handler's own file/line range highlighted after unwrapping any `asyncHandler`.
  6. **Controllers/services**: the handler bodies, their validation schema (Zod/Joi) bound to the endpoint, and their calls into services/repositories.
  7. **Models/data layer**: Mongoose/Sequelize schemas as an entity diagram with relations from `ref`/`hasMany`/`belongsTo`.
  8. **Error handling, last** — mirroring the framework's own rule that error middleware is registered last, and narrating where an error thrown in step 6 surfaces.
  Chunking this against the pipeline's existing 90–180s-per-chunk target: steps 1–2 one chunk, step 3 one chunk, step 4 one chunk, then one chunk per router (splitting routers with many endpoints), then models, then error handling.

### Gaps

These are stable, well-known properties but should be verified with a citation before the report asserts them.
- I found no benchmark or study comparing accuracy of Express endpoint extraction across tools; the accuracy claims here are limited to what each tool's own documentation admits.
