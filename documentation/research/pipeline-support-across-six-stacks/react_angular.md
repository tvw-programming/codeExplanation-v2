# React and Angular: what a static analyzer must understand to narrate a source file

Scope note: findings below are drawn from official React (react.dev) and Angular (angular.dev) docs, the TypeScript Compiler API wiki, Compodoc's own site/README, and the tree-sitter TypeScript grammar package. Where a claim is an engineering inference rather than something a source states, it is placed under **Inferences**. Where I could not source something, it is in **Gaps** — notably Compodoc's internal parser choice and formal/academic citations for regex limits.

## React: what are the units of meaning a viewer needs explained, and which resist regex extraction?

### Takeaway
For React the unit of meaning is the **component plus the state it owns plus the props contract plus the hook calls at its top level** — and the "what does it render" answer lives in JSX, which is a nested, expression-bearing sub-language that a line/regex scanner cannot segment. Hooks, custom hooks and wrapper HOCs (`memo`, `forwardRef`, `lazy`) are the specific constructs where naive extraction silently loses the component identity.

### Cited Findings
- React's own framing of a component's meaning is ownership of state plus downward props plus upward callbacks: "Instead of duplicating shared state between components, *lift it up* to their common shared parent, and *pass it down* to the children that need it." For each piece of state you "choose the component that 'owns' it" — single source of truth — and a child can only change it because the parent "explicitly allow[s]" it by passing a handler. — [React: Sharing State Between Components](https://react.dev/learn/sharing-state-between-components)
- The same page defines the controlled/uncontrolled distinction that a narration must get right: an uncontrolled component holds its own `useState`, a controlled one is "driven by props"; most real components mix both. — [React: Sharing State Between Components](https://react.dev/learn/sharing-state-between-components)
- Hooks are only legal in two syntactic positions, which is exactly the fact an extractor can exploit: "Only call Hooks at the top level" — not inside loops, conditions, nested functions, `try`/`catch`/`finally`, event handlers, class components, or inside callbacks passed to `useMemo`, `useReducer` or `useEffect`; and only from a function component or a custom Hook, not a plain function. — [React: Rules of Hooks](https://react.dev/reference/rules/rules-of-hooks)
- The `use` prefix is load-bearing, not stylistic: "Functions whose names start with `use` are Hooks. This is how React and the ESLint plugin recognize them." Component examples are capitalized (`Counter`, `FriendList`), though the page presents capitalization as convention shown in examples rather than a stated rule. — [React: Rules of Hooks](https://react.dev/reference/rules/rules-of-hooks)
- React recommends `eslint-plugin-react-hooks` to catch violations — i.e. the canonical React-aware static analysis is an ESLint rule running on a Babel/TS ESTree AST, not a text scan. — [React: Rules of Hooks](https://react.dev/reference/rules/rules-of-hooks)
- `memo` wraps and *replaces* the component value: `const MemoizedComponent = memo(SomeComponent, arePropsEqual?)`. It "doesn't modify it; it returns a new memoized component," and it accepts "[a]ny valid React component, including functions and `forwardRef` components." The documented idiom nests the definition inside the call: `const Greeting = memo(function Greeting({ name }) { ... })`. — [React: `memo`](https://react.dev/reference/react/memo)

### Inferences
- **Units of meaning to narrate, ranked by payoff:** (1) component identity and kind (function vs class vs wrapped); (2) props contract — the destructured parameter names and, in TS, the `Props` interface/type alias with optionality and defaults; (3) state owned — `useState`/`useReducer` tuple names and initial values; (4) hooks used, split into React built-ins vs project custom hooks (the latter are the interesting narrative: a `useAuth()` call is a whole subsystem reference); (5) effects — `useEffect` dependency arrays and what the body touches (fetch, subscription, timer), since this is where the "why does this re-run" explanation lives; (6) context — `createContext` definition sites vs `useContext` consumption sites, which is the only way to explain data arriving without props; (7) rendered children — the capitalized JSX tags, which give the parent/child edges; (8) conditional/list rendering shape (`&&`, ternary, `.map`), which is what the viewer actually sees on screen.
- **What determines "what it renders":** the set of JSX element names in the return value(s), filtered to capitalized identifiers (components) vs lowercase (DOM elements), plus names appearing in `React.createElement` calls and in the arguments of `lazy(() => import(...))`. Getting this right requires knowing where the return expression ends — a brace-matching problem, not a line-pattern problem.
- **Parent/child graph construction:** the edge is (capitalized JSX tag inside file A) → (import binding in file A resolving to file B). That means the component graph is only as good as the module resolution: path aliases (`@/components/...` from `tsconfig.json` `paths`), barrel `index.ts` re-exports, and default-vs-named imports all have to be resolved before edges are real. A regex extractor that records raw import strings produces a graph with dangling nodes.
- **Where regex breaks for React specifically:**
  - *Arrow components assigned to consts with generics*: `export const Table = <T,>({ rows }: TableProps<T>) => { ... }` — the `<T,>` and `TableProps<T>` angle brackets are indistinguishable from JSX/comparison operators to a scanner; many regexes either treat `<T,>` as a JSX tag or fail to recognize the declaration as a component at all.
  - *`memo`/`forwardRef` wrapping*: `export default memo(forwardRef<HTMLInputElement, Props>(function Input(props, ref) {...}))`. The exported name, the display name, and the inner function name can all differ; a `function X(` or `const X =` pattern misses it entirely, or reports `memo` as the component. Because `memo` returns a new component rather than mutating the original ([React: `memo`](https://react.dev/reference/react/memo)), the *wrapper* is what the parent imports, so the narration must bind the wrapper's exported name to the inner function's body.
  - *`React.lazy` + dynamic import*: `const Settings = lazy(() => import('./Settings'))` is simultaneously a component declaration, a module dependency, and (usually) a route target. Regex typically catalogs it as none of the three.
  - *End-of-component detection*: line ranges for a component require matching `{`/`}` across JSX, nested arrow callbacks, object literals in props (`style={{ ... }}` — double braces), and template literals containing `}` (`` className={`p-${x}`} ``). Balanced-delimiter matching is outside what a single regex can do; the practical symptom is component line ranges that end at the first `}` on column 0, which cuts the render body out of the narrated chunk or merges two components into one chunk.
  - *JSX is not tag-soup-safe*: `<Foo<Bar> prop={a < b} />`, self-closing vs children, fragments `<>...</>`, member expressions as tags (`<Form.Item>`), namespaced/spread props (`{...rest}`), and comments `{/* <Legacy/> */}` all produce false positives/negatives in a tag regex. Commented-out JSX being reported as a rendered child is a particularly damaging narration error because it is confidently wrong.
  - *Event handlers*: handlers are not a syntactic category. They appear as inline arrows in JSX (`onClick={() => setOpen(!open)}`), as consts (`const handleSubmit = async (e) => {...}`), as class methods, as `useCallback` results, and as props passed down (`onShow` in React's own example — [React: Sharing State Between Components](https://react.dev/learn/sharing-state-between-components)). A `handle*`/`on*` naming regex gets the common case and misses the rest; worse, it cannot tell a *handler definition* from a *handler being forwarded*, which is the distinction that explains the component's role.
  - *Hooks*: because hooks must be top-level in the component body ([Rules of Hooks](https://react.dev/reference/rules/rules-of-hooks)), a scanner that grabs every `use[A-Z]\w*(` in the file will also pick up hook calls from a second component in the same file, from a commented example, or from a string. Attributing hooks to the right component requires the component's true body range — the same brace problem.
  - *API calls*: `fetch(`/`axios.get(` with a template-literal URL (`` `${BASE}/users/${id}` ``) yields a URL that is only knowable as an expression; method is often in an options object on a later line (`{ method: 'PATCH' }`), and many codebases route all calls through a generated client (`api.users.update(...)`) where no HTTP verb appears in the file at all.
  - *Class components*: `state = { ... }` class property, `this.setState`, lifecycle methods, and `static contextType` are a completely different extraction target from hooks; a single regex set tuned for hooks reports a class component as having no state.
- **Practical consequence for a narrated-video pipeline:** the two most damaging React failure modes are (a) wrong line ranges, which desynchronizes the highlighted code region from the voiceover, and (b) wrong component identity under `memo`/`forwardRef`/HOC, which makes the narration name a thing the viewer cannot find on screen.

### Gaps
- react.dev's `forwardRef` page was not fetched directly; the only sourced statement about `forwardRef` here is `memo`'s page noting it accepts forwardRef components, plus its appearance under "Legacy APIs" in that page's sidebar. The current status of `forwardRef` in React 19+ (ref-as-prop) is not sourced here.
- No source found in this pass for render-props / HOC patterns as documented React concepts; treated as inference only.

## Angular: what are the units of meaning, and how does the decorator-and-metadata model differ from React?

### Takeaway
Angular's unit of meaning is a **decorated class plus its metadata object plus a separate template file**, with wiring expressed as *data* (metadata arrays, route objects, provider lists) rather than as calls in the render path. A file-local analyzer therefore sees only half of any Angular feature: the class without its template, or the route table without the components it names.

### Cited Findings
- `@Component` takes a metadata object that "includes the `selector`, `template`, and other properties." `selector` is "[a] CSS selector that defines how the component appears in other templates," and "[t]he matching element is the component's host element." — [Angular: Components](https://angular.dev/guide/components)
- Template and styles are each either inline or a separate file: `template` holds inline HTML, `templateUrl` "points to an external HTML file"; `styles` holds inline CSS, `styleUrl` points to an external CSS file. For both, "[p]aths are relative to the component's directory." — [Angular: Components](https://angular.dev/guide/components)
- `imports` is "[a]n array of the components, directives, and pipes the template uses. You must list each one here before using it." — [Angular: Components](https://angular.dev/guide/components)
- Standalone is now the default: "Components are standalone by default, so you can add them directly to another component's `imports`. Components that set `standalone: false` are instead made available by importing their `NgModule`. Before Angular 19.0.0, the default was `false`." — [Angular: Components](https://angular.dev/guide/components)
- Templates reference class members by name and signals are read by invocation: template expressions "refer to component class members by name, such as `theme` or `isFormValid()`," and signals are read by calling them, like `theme()`, with Angular tracking those reads to update the view. Interpolation is `{{ expression }}`; property binding is `[disabled]="isFormValid()"`; attribute-only targets use `[attr.role]`; class/style bindings include `[class.expanded]`, `[class]`, `[style.height.px]`, `[style]`. — [Angular: Binding dynamic text, properties and attributes](https://angular.dev/guide/templates/binding)
- Routes are plain data in a `Routes` array, "typically exported from a file whose name includes 'routes' (the CLI generates `src/app/app.routes.ts`)", with properties `path` (`''`, `:name`, `**`), `component`, `redirectTo`, `title`, `data`, `providers`, and `children` (nested routes rendered into the parent's `<router-outlet />`). Matching is first-match-wins, so "list specific paths before general ones." Registration in a standalone app is `provideRouter(routes)` inside `ApplicationConfig.providers`. — [Angular: Define routes](https://angular.dev/guide/routing/define-routes)
- Dependency injection in current Angular docs is presented through `inject()`: "You call `inject(SomeType)` to get a dependency, typically as a class field initializer (`private router = inject(Router);`). You can also call it in the constructor body. It works in components, directives, services, and functions such as route guards, anywhere Angular calls it an injection context." The page also describes a `@Service` decorator as shorthand for `@Injectable({providedIn: 'root'})`, making the class "available throughout your entire application as a singleton." — [Angular: Dependency injection](https://angular.dev/guide/di)
- Compodoc — the Angular-specific doc generator — documents exactly this set of units: "components, directives, pipes, modules, injectables, guards, interceptors, classes, and interfaces," plus "standalone APIs, signal inputs and aliases, `styleUrl`, injectable metadata, and inheritance details," routing including "`provideRouter`, lazy routes, default-export route files, and classic NgModule routing," and it generates "route and dependency graphs" and a documentation coverage report. — [Compodoc README](https://github.com/compodoc/compodoc)
- Compodoc states it does not typecheck: "No TypeScript compilation - Compodoc just parses your code." Its API table of contents is "generated using elements found during file parsing," and it understands the JSDoc tags `@param`, `@returns`, `@link`, `@ignore`, `@example`. — [Compodoc: Features](https://compodoc.app/guides/features.html)

### Inferences
- **The fundamental difference from React:** React expresses composition *imperatively in the render path* — the child appears as a JSX tag inside the parent's returned expression, in the same file, in the same language. Angular expresses composition *declaratively as metadata and markup*: the parent's `imports` array names the child class, and the child is actually instantiated by a CSS selector match inside an HTML file that the TypeScript file merely references by path ([Angular: Components](https://angular.dev/guide/components)). So in React the component graph is recoverable from the TS/TSX AST alone; in Angular it is recoverable only by joining three facts — the `imports` array (what is allowed), the `selector` registry across the whole project (name → class), and the template's element names (what is actually used).
- **Selector matching is a project-wide index, not a file-local lookup.** Because `selector` is a CSS selector and the template is HTML, resolving `<app-user-card [user]="u">` to `UserCardComponent` requires having previously indexed every `@Component`/`@Directive` selector in the repo. This is a two-pass requirement: pass 1 builds the selector/pipe-name index; pass 2 narrates files. Attribute selectors (`[appHighlight]`) and pipes (`{{ x | currency }}`) mean the index has three namespaces (element, attribute, pipe name), and directives are invisible in markup except as attributes.
- **The "one source file = one chunk" model is broken for Angular, concretely:** a single logical unit is 2–4 files — `user-card.component.ts` (class, inputs/outputs, injected services, handler methods), `user-card.component.html` (the actual UI, the bindings, the child components, the event wiring), `user-card.component.scss` (irrelevant to narration except as a mention), and often `user-card.component.spec.ts`. Narrating the `.ts` alone produces an explanation with no UI in it; narrating the `.html` alone produces an explanation with no logic. The fix is a **component bundle chunk**: resolve `templateUrl`/`styleUrl`/`styleUrls` relative to the component's directory ([Angular: Components](https://angular.dev/guide/components)) at chunk-planning time, parse the HTML with an HTML parser, and emit one chunk whose narration crosses both files — with the video cutting between the class and the template, since that mirrors how an Angular developer actually reads the code.
- **Template parsing is a second grammar, not a sub-case.** Angular templates contain: interpolations with arbitrary Angular expressions, `[prop]`, `(event)`, `[(ngModel)]`, `[attr.x]`, `[class.x]`, `[style.x.px]` ([Angular: binding](https://angular.dev/guide/templates/binding)), structural directives in both legacy (`*ngIf`, `*ngFor`) and current block syntax (`@if`, `@for`, `@switch`, `@defer`), template reference variables (`#ref`), `<ng-content>`, `<ng-template>`/`<ng-container>`, and `<router-outlet>`. The new `@`-block syntax is especially hostile to regex because `@if (cond) { ... } @else { ... }` introduces brace nesting *inside HTML*, so neither an HTML tag scanner nor a brace counter alone is sufficient.
- **Binding direction is the narration's core content.** `[x]="expr"` is data flowing in, `(y)="handler()"` is an event flowing out, `[(z)]` is both. Extracting the *direction* plus the *class member referenced* (which the docs say is referenced by name — [binding](https://angular.dev/guide/templates/binding)) is what lets a narrator say "when the user clicks Save, the template calls the component's `save()` method, which calls `UserService.update()`." That sentence requires template + class + service, i.e. three files.
- **The DI graph:** Angular's DI is a real graph and the single most valuable thing to extract for an architecture-level narration, because it is the backend-ish dependency structure of the app. Two syntactic forms must both be handled: (a) current docs style, `private router = inject(Router);` as a field initializer or in the constructor body ([Angular: DI](https://angular.dev/guide/di)); (b) legacy and still extremely common constructor-parameter injection, `constructor(private http: HttpClient, @Inject(CONFIG) private cfg: AppConfig) {}`, where the dependency is encoded in the **TypeScript parameter type annotation** of a parameter-property. Form (b) is the hard case for regex: multi-line constructor signatures, access modifiers (`private readonly`), parameter decorators (`@Inject`, `@Optional`, `@Self`, `@SkipSelf`), generic types (`Repository<User>`), union/optional types, and default values all appear in the parameter list, and a comma-split on the signature text misdivides on commas inside generics (`Map<string, User>`). Resolving the *type name* to a project class additionally needs the import map.
- **Provider resolution is scope-sensitive.** `@Injectable({providedIn:'root'})` (or the `@Service` shorthand — [Angular: DI](https://angular.dev/guide/di)) is app-wide; `providers: [...]` on a component, a route ([define-routes](https://angular.dev/guide/routing/define-routes) lists route-level `providers`), or an NgModule is scoped; `{provide: X, useClass: Y}`, `useFactory`, `useValue`, `useExisting` and `multi: true` mean the injected *type* is not necessarily the implementing *class*. A narration that says "this component uses `PaymentService`" when the route provides `MockPaymentService` for `PaymentService` is wrong in a way viewers will notice.
- **Routing is where the Angular narration should start.** Routes are data ([define-routes](https://angular.dev/guide/routing/define-routes)), so the route table is a near-perfect table of contents for the app: path → component/loadComponent, nesting → shell/outlet structure, `loadChildren`/`loadComponent` → feature boundaries, guards → access rules. Extracting it needs object-literal parsing (nested `children` arrays, `canActivate: [authGuard]`, `loadComponent: () => import('./x').then(m => m.X)`), which is nested-brace territory again; and lazy route files that use `export default` ([Compodoc README](https://github.com/compodoc/compodoc) lists "default-export route files" as a case it handles) break name-based matching.
- **NgModules still matter even though standalone is the default** ([Angular: Components](https://angular.dev/guide/components)): a mixed-era codebase has both, so the analyzer needs `@NgModule({declarations, imports, exports, providers, bootstrap})` handling *and* standalone `imports` handling, and must not report a `standalone: false` component as having no template context.
- **RxJS is an Angular-specific narrative obligation.** Service methods return `Observable<T>`; components consume them via `subscribe`, `async` pipe in the template, `takeUntilDestroyed`, or `toSignal`. Explaining an Angular service without saying "this returns a stream you must subscribe to, and the template's `| async` does that for you" leaves the viewer unable to read the code. Detecting it means recognizing the return *type annotation* and the pipe operators chained inside `.pipe(map(...), switchMap(...))` — multi-line, nested call chains.

### Gaps

The features page explicitly says "No TypeScript compilation - Compodoc just parses your code" ([Compodoc: Features](https://compodoc.app/guides/features.html)), which implies syntax-level parsing without a type checker, but the concrete dependency is unverified here.
- `angular.dev/guide/di` as fetched presents `inject()` and a `@Service` decorator shorthand and did **not** cover constructor-parameter injection, `providers` arrays, `InjectionToken`, or `@Inject`. Constructor-parameter injection and `@Inject` are described above from engineering knowledge of real codebases, not from a fetched source — flagging this explicitly because the doc site's current framing has moved to `inject()`. The `@Service` decorator is also newer than my training baseline; it appeared in the live doc page, so I report it as the page states it. A reader should re-verify the DI section before the pipeline hard-codes either form as "the" idiom.

## What tools and approaches parse React/Angular well, and what are realistic options for a Python pipeline?

### Takeaway
The authoritative parsers are all JavaScript-side (TypeScript Compiler API, ts-morph, Babel, `@angular/compiler`); for a Python pipeline the two realistic routes are **tree-sitter via `tree-sitter-typescript` in-process** (fast, syntax-only, good enough for structure) or **a small Node sidecar/CLI that emits JSON** (full fidelity, type information, Angular-aware).

### Cited Findings
- The TypeScript Compiler API offers: `ts.createProgram` building a `Program`, "the TypeScript terminology for your whole application"; a `CompilerHost` abstracting file reading; `ts.createSourceFile`, which "parses a file into a `SourceFile` that holds both the text and the AST"; `Node` as "the root interface for the TypeScript AST"; traversal via recursive `ts.forEachChild`; and `program.getTypeChecker()` exposing `getSymbolAtLocation`, `getTypeAtLocation`, `getTypeOfSymbolAtLocation`, `typeToString`. It also provides `ts.transpileModule` and factory/printer APIs. Its linter example "shows that a type checker is unnecessary when you only need to traverse a file's syntax tree." — [TypeScript wiki: Using the Compiler API](https://github.com/microsoft/TypeScript/wiki/Using-the-Compiler-API)
- ts-morph "wraps the TypeScript compiler API" to make "setup, navigation, and manipulation of the TypeScript AST simpler." Its docs cover navigation, manipulation and emitting; the fetched page did not document type-checker or find-references features, and notes some features are undocumented. — [ts-morph](https://ts-morph.com/)
- `tree-sitter-typescript` provides "TypeScript and TSX grammars for tree-sitter," as **two separate grammars** "because TypeScript and TSX are different dialects"; the `tsx` grammar can also parse JS with Flow annotations. It is published on PyPI (version 0.23.2, released 2024-11-11), requires Python 3.9+, MIT licensed; the page's only usage example is JavaScript. — [PyPI: tree-sitter-typescript](https://pypi.org/project/tree-sitter-typescript/)
- React points to `eslint-plugin-react-hooks` as the tool that enforces hook rules — i.e. React's own recommended static analysis path is the ESLint/ESTree ecosystem. — [React: Rules of Hooks](https://react.dev/reference/rules/rules-of-hooks)
- Compodoc is the Angular-specific precedent and already emits exactly the artifacts a video pipeline wants: route graph, dependency graph, JSON export, and "LLM-ready Markdown." — [Compodoc README](https://github.com/compodoc/compodoc)

### Inferences
- **Recommended architecture for a Python pipeline (tiered):**
  1. *Tier 1 — tree-sitter in-process (`pip install tree-sitter tree-sitter-typescript`).* Load the `typescript` grammar for `.ts` and the `tsx` grammar for `.tsx` — note the two grammars are genuinely separate ([PyPI](https://pypi.org/project/tree-sitter-typescript/)), so the pipeline must pick per extension, and a `.ts` file containing JSX will fail or mis-parse under the `typescript` grammar. Use tree-sitter **queries** (S-expression patterns) to extract declarations, JSX element names, call expressions, decorators, class members and exact byte/line spans. This immediately and correctly solves the brace/line-range problem, because node extents come from the parser. It is error-tolerant, which matters for a pipeline that must not crash on one odd file.
  2. *Tier 2 — Node sidecar for semantics.* A ~200-line Node script using ts-morph ([ts-morph](https://ts-morph.com/)) or the raw compiler API ([TS wiki](https://github.com/microsoft/TypeScript/wiki/Using-the-Compiler-API)) that reads `tsconfig.json`, builds a `Program`, and dumps JSON: resolved imports (honoring `paths` aliases), prop type members with optionality, inferred types of `useState` tuples, and resolved symbols for JSX tags. This is the only way to get the type-level facts (`Observable<User>` vs `User`, prop interface members inherited from another interface) that make narration accurate.
  3. *Tier 3 — Angular templates.* Parse `.html` with an HTML parser that preserves attribute names and source positions. In Python, `lxml`/`html5lib` will preserve `[prop]`/`(event)` as ordinary attribute names (they are valid-ish attribute text), which is enough to classify binding direction and extract the expression string; the Angular expression inside the quotes then needs either a light expression parse or to be passed through to the LLM verbatim. `@if`/`@for` blocks are not HTML and need a pre-pass. If fidelity matters, `@angular/compiler` in the Node sidecar is the correct parser (status unverified — see Gaps).
- **Babel (`@babel/parser`) vs TypeScript compiler:** Babel parses TSX fine and is faster, but discards type semantics; it is the right choice only if you need JSX structure and nothing type-level. ESLint's `@typescript-eslint/parser` produces an ESTree-shaped AST backed by the TS parser and is the natural host if you want to express extraction rules as lint rules.
- **Python-only JS parsers are a trap here.** `esprima-python`/`pyjsparser` handle ES5/ES6 JavaScript, not TypeScript type syntax, generics, decorators or JSX, so they will fail on essentially every file in a modern React or Angular repo. Do not treat them as a fallback.
- **Reuse rather than reimplement for Angular:** running Compodoc once over the repo and consuming its JSON export gives route graph, DI/dependency graph, and per-class member documentation for free ([Compodoc README](https://github.com/compodoc/compodoc)), which is a large fraction of the Angular extraction problem. Its own "LLM-ready Markdown" output suggests it is already being used as an LLM feed. Caveat: it is Angular-only and provides nothing for React.

### Gaps
- No Python usage example on the `tree-sitter-typescript` PyPI page ([PyPI](https://pypi.org/project/tree-sitter-typescript/)); the `py-tree-sitter` binding API (`Language`, `Parser`, `Query`) and current version compatibility between `tree-sitter` and the grammar wheel were not verified in this pass, and these two packages have historically had version-compatibility constraints. Verify before pinning.
- Compodoc's JSON export schema was not inspected, so I cannot state what fields it contains.
- No benchmark or comparative study found in this pass on accuracy of tree-sitter vs TS compiler API for TS/TSX structure extraction.

## What specifically goes wrong with regex extraction — concrete failure cases

### Takeaway
Regex fails on React/Angular not from sloppiness but from a category error: the needed facts are defined by nested, balanced, multi-line structure (bodies, generics, JSX, object literals, decorator arguments, constructor parameter lists), and a regular expression cannot match balanced delimiters, so every "end of this thing" question is answered wrongly at some rate — which in a narration pipeline manifests as confident, plausible, wrong voiceover.

### Cited Findings
- `tree-sitter-typescript` ships *two separate grammars* because "TypeScript and TSX are different dialects" ([PyPI](https://pypi.org/project/tree-sitter-typescript/)) — direct evidence from the parsing ecosystem that `<` disambiguation (generics vs JSX) cannot be handled by one uniform text-level treatment.
- The TS compiler API exposes node extents through the AST rather than by text matching; a `SourceFile` "holds both the text and the AST" and traversal is structural via `ts.forEachChild` ([TS wiki](https://github.com/microsoft/TypeScript/wiki/Using-the-Compiler-API)) — i.e. the supported way to get a construct's range is to ask the parser.
- Compodoc's position is instructive on the *other* side: it parses without full compilation ("No TypeScript compilation - Compodoc just parses your code" — [Compodoc: Features](https://compodoc.app/guides/features.html)), yet still handles standalone APIs, signal inputs, inheritance and lazy/default-export routes ([Compodoc README](https://github.com/compodoc/compodoc)) — showing that syntax-level parsing (not typechecking) is the real minimum bar, and regex is below it.

### Inferences
Concrete failure catalogue, each with the construct that triggers it:

| Construct | Regex failure | Narration symptom |
|---|---|---|
| `const Table = <T,>({rows}: Props<T>) => {...}` | `<T,>` read as JSX; `Props<T>` breaks a type-capture group | component not detected, or detected with garbage props |
| `export default memo(forwardRef(function Input(p, ref) {...}))` | no `function X(`/`const X =` at top level matching the export | component named `memo`, or missing entirely |
| `style={{margin: 0}}`, `` className={`a-${b}`} `` | brace counting double-counts / template literal `}` closes early | component line range truncated mid-render |
| `{/* <OldThing/> */}` | JSX tag regex matches inside comment | narrates a child that does not render |
| `const [a, setA] = useState<Record<string, User>>({})` | comma-split inside generics | state name/type mangled |
| `constructor(private http: HttpClient,\n  @Inject(CFG) private cfg: Map<string, X>) {}` | multi-line signature + commas in generics + param decorators | DI graph loses or merges dependencies |
| `@Component({ template: `<div>{{a}}</div>`, styles: [`...`] })` | decorator argument is a nested object with template literals containing braces and `)` | metadata object truncated; selector/templateUrl missed |
| `@if (x) { <Foo/> } @else { <Bar/> }` in `.html` | neither HTML-tag nor brace scanning alone covers it | conditional UI mis-described |
| `loadChildren: () => import('./admin/routes').then(m => m.ADMIN_ROUTES)` | nested arrow + call chain in an object value | lazy feature boundary invisible |
| `` fetch(`${API}/users/${id}`, {method:'PATCH'}) `` | URL is an expression; verb is on another line | API call reported with literal `${API}` or wrong verb |
| `.pipe(map(u => u.name), switchMap(n => this.s.get(n)))` | nested multi-line call chain | RxJS data flow not explained |
| `function Outer(){ function Inner(){ useState() } }` | hook attributed to wrong function | wrong state ownership — the single most misleading React error |
| `interface Props extends BaseProps { ... }` | inherited members invisible to a file-local scan | props contract reported as incomplete |
| path alias `import X from '@/features/x'` | raw string recorded, no resolution | dependency graph has dangling edges |
| `export { Button } from './Button'` (barrel) | re-export treated as a declaration | phantom component node |

Additional structural points:
- **Balanced delimiters:** matching `{`…`}` across arbitrary nesting is not expressible as a regular expression (it requires a stack / recursive descent). Every "line range of this function/component/metadata object" requirement in the existing pipeline is therefore approximate by construction. PCRE recursion (`(?R)`) can fake it but Python's `re` cannot; `regex` module recursion plus string/comment/template-literal awareness is effectively a hand-written parser with worse ergonomics than tree-sitter.
- **Lexer-level ambiguity:** `<` is generic-open, less-than, or JSX-open depending on parser state; `/` is divide or regex-literal or JSX-close; backtick starts a template literal that can contain `${ ... }` holding arbitrary code including more template literals and more braces. These require tokenizer state, not patterns.
- **Severity ordering for a narration product:** silent wrong attribution (hook/state/dependency assigned to the wrong declaration) > truncated ranges (highlight desync) > missed items (incomplete but honest). A pipeline moving incrementally should fix attribution first, which in practice means getting true node ranges — the cheapest single upgrade being tree-sitter for range/declaration discovery while keeping existing regexes for within-node detail.

## Narrative ordering: what makes a React or Angular codebase comprehensible on video

### Takeaway
Both frameworks want a top-down, entry-point-first order, but the spine differs: **React's spine is the component tree reached from the router/App**, while **Angular's spine is the route table → feature boundaries → component bundles → injected services**, because Angular's wiring is declarative data that can be read before any component.

### Cited Findings
- Angular's routes are plain exported data (`src/app/app.routes.ts` by CLI convention) registered via `provideRouter(routes)` in `ApplicationConfig.providers`, with `children` nesting rendered through `<router-outlet />` and first-match-wins ordering. — [Angular: Define routes](https://angular.dev/guide/routing/define-routes)
- Compodoc's own output structure for Angular is: modules/components/directives/pipes/injectables/guards/interceptors/classes/interfaces, plus route and dependency graphs and a coverage report — an implicit, battle-tested ordering of Angular units. — [Compodoc README](https://github.com/compodoc/compodoc)
- React's conceptual explanation order for any interactive UI is state-ownership-first: identify the state, choose the owning component, pass values and handlers down. — [React: Sharing State Between Components](https://react.dev/learn/sharing-state-between-components)
- Hook calls sit at the top of a component body by rule ([Rules of Hooks](https://react.dev/reference/rules/rules-of-hooks)), and `imports`/metadata sit at the top of an Angular component ([Angular: Components](https://angular.dev/guide/components)) — so in both frameworks the file's own top-to-bottom order roughly matches a sensible narration order.

### Inferences
- **React ordering (project level):** `main.tsx`/`index.tsx` entry and providers mounted there (Router, QueryClient, Theme, Store) → router config / route tree → layout shell components → per-feature page components → leaf/presentational components → custom hooks → API client / services layer → types/models → shared utilities. Rationale: the providers at the entry point are what make `useContext`/`useQuery`/`useSelector` later in the tour comprehensible; narrating a `useAuth()` call before showing `AuthProvider` forces a forward reference the viewer cannot hold.
- **React ordering (within a file/chunk):** purpose (from the leading doc comment) → props contract → state owned → hooks used (built-in, then project custom hooks) → effects and what triggers them → handlers → what it renders, including conditional/list structure → which children it composes. Ending on "what it renders" lets the video finish on the visible UI, which is the natural landing point.
- **Angular ordering (project level):** `main.ts` bootstrap + `app.config.ts` providers → `app.routes.ts` (the table of contents; also gives the lazy-loaded feature boundaries) → guards/interceptors (cross-cutting, explains auth and HTTP behavior once) → per-feature: routes → container component bundle (class + template) → child components → the services those components inject → the models those services return. Rationale: Angular's route table is data ([define-routes](https://angular.dev/guide/routing/define-routes)) so it can be read and narrated accurately *before* any component, giving the viewer a map first; and because DI is pervasive, services must be introduced when first injected rather than in a lump at the end.
- **Angular ordering (within a component bundle chunk):** selector and where this component appears in a parent template → inputs/outputs (the contract) → injected dependencies (the DI line, which is the "what subsystems does this touch" sentence) → the template: structure, bindings in, events out → the handler methods the template calls → the service calls those handlers make and the Observables/signals they return → styles (mention only). This order deliberately crosses the .ts/.html boundary twice, which is the point.
- **Cross-cutting narration rules for both:** (1) establish the dependency direction before the detail — a viewer who knows "this is a leaf presentational component" interprets the rest differently than for a container; (2) prefer an edge-ordered tour (parent before child, provider before consumer) over alphabetical-by-filename, which is the default a naive pipeline produces and the single biggest comprehension loss; (3) degrade honestly — when the extractor's confidence is low (unresolved alias, dynamic import, factory provider), the narration should say "this resolves at runtime" rather than assert a resolution, since a confident wrong statement in audio is unverifiable by the viewer mid-video.
- **Chunking implication:** React's natural chunk is the file (often 1 component per file); Angular's natural chunk is the *directory-local bundle* (`*.component.ts` + resolved `templateUrl` + resolved `styleUrl(s)`), with `*.spec.ts` excluded. The chunk planner therefore needs framework detection before chunking, not after — detect Angular by `angular.json`/`@angular/core` in `package.json`/presence of `@Component` decorators, and React by `react` in `package.json`/`.tsx` with JSX.

### Gaps
- No source found in this pass that studies comprehension ordering for code-explanation video or narrated code walkthroughs specifically; all ordering recommendations above are inference from the frameworks' own documentation structure and from Compodoc's output organization, not from evidence about viewer comprehension.
